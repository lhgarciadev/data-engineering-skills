# Research: full load (truncate-and-reload) para `sql-data-engineering`

**Fecha:** 2026-07-30
**Alcance:** el skill `sql-data-engineering` (`references/engineering-query-patterns.md`) ya documenta carga incremental idempotente vía `MERGE`/upsert y SCD Type 2, pero no tiene cobertura del patrón opuesto — **full load / truncate-and-reload** como estrategia deliberada — pese a ser una decisión de diseño real (tablas de dimensión pequeñas, tablas de staging, reconstrucción tras un cambio de esquema). 4 investigaciones en paralelo contra documentación oficial: postgresql.org/docs, dev.mysql.com/doc/refman, learn.microsoft.com (vía el MCP oficial de Microsoft Learn), docs.snowflake.com, cloud.google.com/bigquery/docs, docs.aws.amazon.com/redshift, docs.getdbt.com. Cuatro de las afirmaciones más "cargadas" (la más contraintuitivas o las que sostienen la recomendación central del futuro contenido del skill) se re-verificaron con un fetch independiente antes de escribir este documento: `ALTER TABLE ... SWAP WITH` de Snowflake, la inclusión de `TRUNCATE TABLE` en transacciones multi-statement de BigQuery, la mecánica exacta de `--full-refresh` de dbt, y el commit implícito de `TRUNCATE` en Redshift. Sin fuentes secundarias, salvo donde se marca explícitamente (y en ese caso, descartadas o señaladas como no verificables).

## 1. TRUNCATE vs. DELETE por motor

### Tabla resumen

| Motor | TRUNCATE es... | ¿Rollback-able en transacción? | Lock vs. DELETE | Restricción por FK |
|---|---|---|---|---|
| PostgreSQL | No etiquetado como "DDL" en su propia página, pero agrupado con DDL no-MVCC-safe en el capítulo de MVCC | **Sí** — transaccional, incluye el reset de sequence si se usa `RESTART IDENTITY` | `ACCESS EXCLUSIVE` (misma clase de lock que `DROP TABLE`) vs. locks de fila de `DELETE` | Falla si hay FK desde otra tabla no incluida en el mismo comando, salvo `CASCADE` |
| MySQL | DDL explícito (doc lo dice literalmente) | **No** — implica commit, "cannot be rolled back"; ni siquiera puede ejecutarse dentro de una transacción | Drop-and-recreate de la tabla (mecanismo distinto a locking de filas) | Falla si hay FK desde otra tabla (InnoDB/NDB); FK entre columnas de la misma tabla sí se permite |
| SQL Server | DDL explícito (doc lo dice literalmente), pero pese a serlo **sí es transaccional** | **Sí** — doc trae un ejemplo completo de `BEGIN TRAN; TRUNCATE; ROLLBACK` que restaura las filas | `SCH-M` (schema modification) + lock de página, no de fila; menos log que `DELETE` | Falla si la tabla es referenciada por FK desde **cualquier** otra tabla (excepción: FK auto-referenciada) |
| Snowflake | DML explícito (doc lo dice literalmente — "the term DML refers to INSERT, UPDATE, DELETE, MERGE, and TRUNCATE") | Se infiere que sí (ver detalle abajo) — no hay ejemplo directo verificado | No hay lenguaje de locking específico para TRUNCATE; el modelo de Snowflake no usa locks de fila tradicionales para tablas estándar | No aplica — Snowflake no tiene el concepto de FK bloqueante |
| BigQuery | DML explícito, listado junto a `INSERT`/`UPDATE`/`DELETE`/`MERGE` como soportado dentro de transacciones multi-statement | **Sí** — verificado, ver detalle abajo | No hay locking de filas tradicional; usa cancelación de transacciones en conflicto (snapshot isolation) | No aplica — BigQuery no enforcea FK |
| Redshift | Ambiguo en la propia doc: la misma frase de "Isolation levels" lista `TRUNCATE` bajo DML y `TRUNCATE TABLE` bajo DDL | **No** — commit implícito, verificado con ejemplo textual `BEGIN; TRUNCATE; ROLLBACK` que **no** restaura las filas | No hay lenguaje de locking de fila específico; usa write locks + serializable/snapshot isolation | No aplica — FK es solo informacional para el optimizer, nunca bloquea `TRUNCATE` |

### Detalle por motor

**PostgreSQL** — verbatim: *"TRUNCATE is transaction-safe with respect to the data in the tables: the truncation will be safely rolled back if the surrounding transaction does not commit."* Con `RESTART IDENTITY`, el reset de la sequence también es transaccional. Lock: *"TRUNCATE acquires an ACCESS EXCLUSIVE lock on each table it operates on, which blocks all other concurrent operations on the table."* FK: *"TRUNCATE cannot be used on a table that has foreign-key references from other tables, unless all such tables are also truncated in the same command."* — `CASCADE` fuerza la inclusión, `RESTRICT` (default) rechaza. Identity: reset es opt-in vía `RESTART IDENTITY` (default es `CONTINUE IDENTITY`, sin reset), a diferencia de `DELETE`, cuya página no menciona sequences en absoluto.
Fuentes: [TRUNCATE — PostgreSQL 18 Documentation](https://www.postgresql.org/docs/current/sql-truncate.html), [13.6. Caveats](https://www.postgresql.org/docs/current/mvcc-caveats.html), [13.3. Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html)

**MySQL** — el motor más restrictivo de los seis. Verbatim: *"it cannot be rolled back like a DML operation"* y, en la página de `DELETE`: *"Unlike DELETE, TRUNCATE TABLE cannot be used within a transaction or if you have a lock on the table."* Clasificación explícita: *"Although TRUNCATE TABLE is similar to DELETE, it is classified as a DDL statement rather than a DML statement."* Confirmado además en la página de implicit-commit, donde `TRUNCATE TABLE`, `RENAME TABLE` y `CREATE TABLE` están listados como sentencias DDL que causan commit implícito. Mecanismo interno en InnoDB: *"Truncate operations drop and re-create the table"* (y, si la tabla vive en un file-per-table tablespace, ese tablespace se dropea y recrea). FK: *"TRUNCATE TABLE fails for an InnoDB table or NDB table if there are any FOREIGN KEY constraints from other tables that reference the table."* `AUTO_INCREMENT`: *"Any AUTO_INCREMENT value is reset to its start value. This is true even for MyISAM and InnoDB, which normally do not reuse sequence values"* — contraste directo con `DELETE FROM tbl_name` sin `WHERE`, que en InnoDB/MyISAM **no** resetea el contador.
Fuentes: [15.1.37 TRUNCATE TABLE Statement](https://dev.mysql.com/doc/refman/8.4/en/truncate-table.html), [15.2.2 DELETE Statement](https://dev.mysql.com/doc/refman/8.4/en/delete.html), [15.3.3 Statements That Cause an Implicit Commit](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html)

**SQL Server** — el caso más contraintuitivo: es DDL y sin embargo sí es transaccional. Confirmado con un ejemplo trabajado oficial ("C. Roll back a truncate operation") que hace `BEGIN TRANSACTION; TRUNCATE TABLE ...; ROLLBACK TRANSACTION;` y muestra las filas restauradas. Clasificación DDL confirmada en la página de taxonomía de sentencias T-SQL, que lista `TRUNCATE TABLE` junto a `ALTER`/`CREATE`/`DROP`/`RENAME`; consistente con que el permiso mínimo requerido es `ALTER` (no `DELETE`). Lock, verbatim: *"TRUNCATE TABLE always locks the table (including a schema (SCH-M) lock) and page, but not each row"*, contra `DELETE`, que adquiere `IX` en tabla/páginas y `X` en cada fila modificada. Logging: *"TRUNCATE TABLE removes the data by deallocating the data pages used to store the table and index data and records only the page deallocations in the transaction log"*, vs. `DELETE`, que registra una entrada por fila eliminada. FK, verbatim: *"You can't use TRUNCATE TABLE on tables that: Are referenced by a FOREIGN KEY constraint. You can truncate a table that has a foreign key that references itself."* — sin excepción para tabla referenciante vacía. Identity: *"the counter for that column is reset to the seed value defined for the column"*; usar `DELETE` si se quiere retener el contador. Nota de plataforma: en Azure Synapse Analytics / PDW (no en SQL Server standalone) la doc dice explícitamente *"TRUNCATE TABLE can't be executed inside of a transaction"* — comportamiento opuesto al de SQL Server standalone, otro caso (como con `MERGE`, ya documentado en el skill) donde Synapse diverge del producto base.
Fuentes: [TRUNCATE TABLE (Transact-SQL)](https://learn.microsoft.com/en-us/sql/t-sql/statements/truncate-table-transact-sql), [DELETE (Transact-SQL)](https://learn.microsoft.com/en-us/sql/t-sql/statements/delete-transact-sql), [Transact-SQL statements](https://learn.microsoft.com/sql/t-sql/statements/statements)

**Snowflake** — clasificación explícita y sorprendente: *"The term DML refers to INSERT, UPDATE, DELETE, MERGE, and TRUNCATE statements"*, mientras que *"The term DDL includes CTAS statements (CREATE TABLE AS SELECT) as well as other DDL statements."* Es decir, Snowflake clasifica `TRUNCATE` como DML y CTAS como DDL — exactamente al revés de MySQL, donde ambos son DDL. De la doc de transacciones: *"DDL statements implicitly commit active transactions"* y *"Each DDL statement executes as a separate transaction... you cannot roll back a DDL statement."* Dado que `TRUNCATE` está bucketeado como DML (no DDL) por la misma página, la implicación directa es que participa normalmente de un bloque `BEGIN...ROLLBACK` explícito, igual que `DELETE`. **Flag de honestidad epistémica:** no se encontró un ejemplo trabajado que muestre un `TRUNCATE` siendo revertido con `ROLLBACK` (a diferencia de SQL Server y Redshift, que sí traen el ejemplo textual) — esta conclusión se apoya en la clasificación DML documentada + las reglas generales de transacciones, no en una demostración directa. Sin lenguaje de locking específico para `TRUNCATE` (la sección de locking nombra `UPDATE`/`DELETE`/`MERGE`/`INSERT` explícitamente, pero no `TRUNCATE`). No aplica FK. Diferencia real con `DELETE`: *"when a table is truncated, the load metadata cannot be recovered"* (se pierde el historial de carga desde archivos externos, algo que `DELETE` preserva).
Fuentes: [Transactions | Snowflake Documentation](https://docs.snowflake.com/en/sql-reference/transactions), [TRUNCATE TABLE](https://docs.snowflake.com/en/sql-reference/sql/truncate-table), [DELETE](https://docs.snowflake.com/en/sql-reference/sql/delete)

**BigQuery** — igual que Snowflake, clasifica `TRUNCATE` como DML, con una consecuencia práctica verificada de forma independiente: *"DML statements: INSERT, UPDATE, DELETE, MERGE, and TRUNCATE TABLE"* están soportadas dentro de transacciones multi-statement, y *"DDL statements that create or drop permanent entities, such as datasets, tables, and functions, are not supported inside transactions."* Un `TRUNCATE TABLE` dentro de `BEGIN TRANSACTION ... ROLLBACK TRANSACTION` sí se revierte — comportamiento opuesto al de Redshift pese a que ambos derivan conceptualmente de un motor analítico columnar. Es *"a metadata operation and does not incur a charge"*; no soporta truncar vistas, vistas materializadas, modelos ni tablas externas. No hay locking de fila tradicional — BigQuery usa snapshot isolation con cancelación de transacciones en conflicto para DML "mutante" (`UPDATE`/`DELETE`/`MERGE`); no se encontró confirmación explícita de que `TRUNCATE TABLE` comparta la misma cuota de concurrencia (2 concurrentes / 20 en cola) que esos tres — la doc solo nombra esos tres verbos en esa cuota específica. FK no aplica: *"BigQuery doesn't enforce primary and foreign key constraints."* No se encontró página oficial confirmando o negando si BigQuery tiene columnas identity/auto-increment nativas (no las tiene, pero eso se infirió por ausencia en la sintaxis de `CREATE TABLE`, no por una afirmación explícita — flag).
Fuentes: [Multi-statement transactions | BigQuery](https://docs.cloud.google.com/bigquery/docs/transactions) (re-verificado con fetch independiente), [Transform data with data manipulation language (DML)](https://docs.cloud.google.com/bigquery/docs/data-manipulation-language), [Use primary and foreign keys | BigQuery](https://docs.cloud.google.com/bigquery/docs/primary-foreign-keys)

**Redshift** — divergencia real y documentada respecto de PostgreSQL vainilla (del que Redshift deriva), verificada con fetch independiente. Verbatim: *"TRUNCATE is much more efficient than DELETE and doesn't require a VACUUM and ANALYZE. However, be aware that TRUNCATE commits the transaction in which it is run."* Y explícitamente: *"The TRUNCATE command commits the transaction in which it is run; therefore, you can't roll back a TRUNCATE operation, and a TRUNCATE command may commit other operations when it commits itself."* Ejemplo textual oficial:
```sql
begin;
truncate date;
rollback;
select count(*) from date;
-- count: 0 (la tabla queda vacía pese al rollback)
```
con la aclaración explícita: *"The DATE table remains empty after the ROLLBACK command because the TRUNCATE command committed automatically."* Esto es el opuesto exacto del comportamiento de PostgreSQL — cualquier código o guía que asuma "Redshift es Postgres, así que TRUNCATE es rollback-able" está objetivamente equivocado. Clasificación DDL/DML: la propia doc es **internamente inconsistente** — la página de isolation levels lista `TRUNCATE` bajo DML commands (junto a `COPY`/`DELETE`/`INSERT`/`UPDATE`) y `TRUNCATE TABLE` bajo DDL commands en la misma oración; se reporta la ambigüedad tal cual, sin resolverla por cuenta propia. Restricción adicional real dentro de stored procedures: *"If the stored procedure is called from within a transaction block, it can't issue a COMMIT, ROLLBACK, or TRUNCATE statement"* — con el error textual `ERROR: TRUNCATE cannot be invoked from a procedure that is executing in an atomic context.` FK: *"You can truncate any table, including tables that are referenced in foreign-key constraints"* — consistente con que en Redshift los FK son solo informacionales para el planner, nunca enforced. No se encontró confirmación oficial sobre si `TRUNCATE` resetea el seed de una columna `IDENTITY` — flag.
Fuentes: [TRUNCATE | Amazon Redshift](https://docs.aws.amazon.com/redshift/latest/dg/r_TRUNCATE.html) (re-verificado con fetch independiente), [Isolation levels in Amazon Redshift](https://docs.aws.amazon.com/redshift/latest/dg/c_serial_isolation.html), [Managing transactions | Amazon Redshift](https://docs.aws.amazon.com/redshift/latest/dg/stored-procedure-transaction-management.html)

## 2. CTAS + swap/rename como alternativa zero-downtime a TRUNCATE+INSERT

Los seis motores soportan CTAS (`CREATE TABLE ... AS SELECT` o equivalente) — la sintaxis exacta está confirmada para los seis vía sus respectivas referencias SQL. Lo que varía radicalmente es **cuánto de "construir tabla nueva + swap atómico" es un patrón vendor-endorsed de verdad** vs. algo ensamblado por el practicante a partir de primitivas documentadas por separado.

**Snowflake — el caso más fuerte, con evidencia directa.** `ALTER TABLE ... SWAP WITH` es un comando propósito-construido para esto, y su propia página lo dice en una frase, verbatim, re-verificada con fetch independiente: *"Swap renames two tables in a single transaction."* Es decir, la atomicidad no es una inferencia del practicante — es una garantía textual del comando. Restricción documentada: no se puede swappear una tabla permanente/transient con una temporal (evita colisión de nombres); el workaround son tres `RENAME TO` encadenados. Además, Snowflake documenta explícitamente el framing de "build new + swap" como patrón de **blue-green deployment**, pero esa frase específica vive en la página de **dynamic tables** (`ALTER DYNAMIC TABLE ... SWAP WITH`), no en la página genérica de `ALTER TABLE`: *"Swapping exchanges two dynamic tables' names and contents atomically. This is useful for blue-green deployments: build and validate a new version, then swap it into place."* El mecanismo subyacente (`SWAP WITH`, atomicidad de "single transaction") es idéntico para tablas estándar, pero el framing "recomendado para X" está atado a dynamic tables, no a CTAS+SWAP para tablas planas — distinción a mantener honesta en el skill. Zero-copy cloning (`CREATE TABLE ... CLONE`) es una operación metadata-only para tablas estándar (contraste explícito con hybrid tables, donde clonar sí es size-of-data), y su rendimiento se compara textualmente con CTAS: *"Cloning performance is similar to that of optimized direct bulk loading with CREATE TABLE AS SELECT."*
Fuentes: [ALTER TABLE](https://docs.snowflake.com/en/sql-reference/sql/alter-table) (re-verificado), [Modify dynamic tables](https://docs.snowflake.com/en/user-guide/dynamic-tables/modify), [Clone databases that contain hybrid tables](https://docs.snowflake.com/en/user-guide/tables-hybrid-clone)

**Redshift — segundo caso más fuerte, con evidencia directa.** AWS documenta el patrón completo, con nombre propio, bajo el título **"Performing a deep copy"**, con SQL literal:
```sql
create table sample_namespace.sample_copy ( ... );
insert into sample_namespace.sample_copy (select * from public.sample);
drop table public.sample;
alter table sample_namespace.sample_copy rename to sample;
```
Es decir: CTAS/`INSERT...SELECT` para construir la copia, luego **DROP de la original + RENAME de la copia** — no "rename la vieja a un nombre de respaldo, luego rename la nueva al nombre de producción". Ese segundo patrón (rename-rename, sin drop intermedio) **no está documentado oficialmente**; si el skill lo presenta, debe presentarse como adaptación del practicante, no como texto de AWS. La misma página, al describir la variante "TRUNCATE + reload" (crear tabla temporal vía CTAS, truncar la original, repoblarla), advierte explícitamente sobre el riesgo de pérdida de datos por el commit implícito de `TRUNCATE`: *"TRUNCATE commits immediately, even if it is inside a transaction block. If the TRUNCATE succeeds but the session shuts down before the following INSERT completes, the data is lost."* — es decir, la propia doc de AWS trata DROP+RENAME como más seguro que TRUNCATE+reload para este propósito.
Fuente: [Performing a deep copy | Amazon Redshift](https://docs.aws.amazon.com/redshift/latest/dg/performing-a-deep-copy.html)

**MySQL — mecanismo parcialmente endorsed.** `RENAME TABLE` soporta swap multi-tabla atómico como ejemplo textual oficial: *"With the transaction table locking conditions satisfied, the rename operation is done atomically; no other session can access any of the tables while the rename is in progress"*, con el idiom exacto para intercambiar dos nombres:
```sql
RENAME TABLE old_table TO tmp_table,
             new_table TO old_table,
             tmp_table TO new_table;
```
Pero no se encontró una página que conecte `CREATE TABLE ... SELECT` con este swap como un pipeline de reload nombrado — la mecánica de swap está documentada, la composición con CTAS no. Caveat operacional real: *"CREATE TABLE ... SELECT does not automatically create any indexes for you"* — los índices deben re-crearse antes o después del swap.
Fuentes: [15.1.36 RENAME TABLE Statement](https://dev.mysql.com/doc/refman/8.4/en/rename-table.html), [15.1.20.3 CREATE TABLE ... SELECT Statement](https://dev.mysql.com/doc/refman/8.4/en/create-table-select.html)

**SQL Server / Azure Synapse — endorsed solo en el producto Synapse, no en SQL Server standalone.** SQL Server standalone no tiene CTAS nativo (usa `SELECT...INTO`, cuyo doc aclara que es un proceso en dos pasos no-atómico salvo transacción explícita); CTAS real (`CREATE TABLE AS SELECT`) solo existe en Azure Synapse Analytics / PDW. Ahí sí hay un ejemplo oficial de build-new+swap+drop:
```sql
RENAME OBJECT FactInternetSales TO FactInternetSales_old;
RENAME OBJECT FactInternetSales_new TO FactInternetSales;
DROP TABLE FactInternetSales_old;
```
con la recomendación explícita: *"Try to think 'CTAS first'. If you think you can solve a problem using CTAS then that is generally the best way to approach it."* Esto refuerza el patrón ya documentado en el skill de que Synapse y SQL Server standalone divergen — aquí, en sentido inverso a `MERGE` (donde Synapse tiene restricciones que SQL Server no tiene): acá Synapse tiene una feature (CTAS+swap nombrado oficialmente) que SQL Server standalone ni siquiera puede replicar con la misma sintaxis.
Fuentes: [SELECT - INTO clause (Transact-SQL)](https://learn.microsoft.com/en-us/sql/t-sql/queries/select-into-clause-transact-sql), [CREATE TABLE AS SELECT (CTAS)](https://learn.microsoft.com/azure/synapse-analytics/sql-data-warehouse/sql-data-warehouse-develop-ctas)

**BigQuery — sin patrón nombrado; el idiom vendor-preferido es otro.** No se encontró página oficial que recomiende "build new + swap/rename" como patrón. Al contrario: la doc de clones de tabla dice explícitamente que un clon **no** sirve para este propósito (*"You can't use a clone operation to append data to an existing table"*, casos de uso documentados son dev/test y sandboxes, no reload de producción). El idiom que BigQuery sí endosa para reload completo es `WRITE_TRUNCATE` como write disposition de un load/query/copy job (confirmado atómico: *"Creation, truncation and append actions occur as one atomic update upon job completion"*, aunque esa cita específica vive en la referencia del cliente Python, no en la doc central de BigQuery — nivel de confianza algo menor) o directamente `CREATE OR REPLACE TABLE ... AS SELECT`. `ALTER TABLE ... RENAME TO` existe y su sintaxis está confirmada, pero sin lenguaje de atomicidad explícito adjunto.
Fuentes: [Manage tables | BigQuery](https://docs.cloud.google.com/bigquery/docs/managing-tables), [Introduction to table clones](https://docs.cloud.google.com/bigquery/docs/table-clones-intro), [Class WriteDisposition | Python client libraries](https://docs.cloud.google.com/python/docs/reference/bigquery/latest/google.cloud.bigquery.enums.WriteDisposition)

**PostgreSQL — sin patrón nombrado, solo primitivas.** `ALTER TABLE ... RENAME TO` está documentado (*"There is no effect on the stored data"*), y por la regla general de la página (*"An ACCESS EXCLUSIVE lock is acquired unless explicitly noted"*, con RENAME ausente de la lista de excepciones) se infiere — no se cita textualmente — que toma `ACCESS EXCLUSIVE`. No se encontró ninguna página de PostgreSQL que recomiende o describa "CTAS + RENAME" como técnica de reload; son primitivas documentadas por separado.
Fuentes: [ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html), [CREATE TABLE AS](https://www.postgresql.org/docs/current/sql-createtableas.html)

## 3. `dbt --full-refresh`: mecánica exacta

Verificado con fetch independiente, cita exacta de la doc oficial de dbt: *"To force dbt to rebuild the entire incremental model from scratch, use the `--full-refresh` flag on the command line. This flag will cause dbt to drop the existing target table in the database before rebuilding it for all-time."*

Es decir: **drop-and-recreate, no truncate-and-reload.** Este es un detalle preciso que vale la pena no difuminar en el skill — dbt no trunca la tabla destino y la repuebla, la dropea por completo y la reconstruye desde cero con el `SELECT` del modelo corriendo en modo no-incremental.

**Cuándo es obligatorio vs. opcional:**
- Agregar una columna al modelo y correr `dbt run` (sin full-refresh): *"this column will not appear in your target table."* La columna nueva se pierde silenciosamente si no se fuerza el refresh.
- Quitar una columna y correr `dbt run`: *"dbt run will fail."* — este caso sí es un error duro, no silencioso.
- Recomendación explícita: *"whenever the logic of your incremental changes, execute a full-refresh run of both your incremental model and any downstream models."*
- El config `on_schema_change` (`ignore` default / `fail` / `append_new_columns` / `sync_all_columns`) reduce, pero no elimina, la necesidad de `--full-refresh` — cita textual: *"resulting in fewer --full-refresh scenarios and saving query costs."* Ninguna de sus variantes hace backfill de valores históricos para columnas nuevas: *"None of the on_schema_change behaviors backfill values in old records for newly added columns."* Para eso, la doc recomienda explícitamente `--full-refresh` o updates manuales.
- Nota BigQuery-específica dentro de `sync_all_columns`: *"On BigQuery, changing column types requires a full table scan; be mindful of the trade-offs when implementing."*

**Relación con `unique_key` e `incremental_strategy`:** no se encontró, en ninguna de las dos páginas relevantes (incremental-models, incremental-strategy), una frase genérica que diga explícitamente "full-refresh bypassea/ignora `unique_key`" — flag de honestidad epistémica, no forzar esa cita si se escribe el skill. Sí hay evidencia indirecta fuerte de que la relación es dependiente de la estrategia, no universal: `unique_key` no aplica a todas las estrategias por igual (*"the insert_overwrite strategy does not use unique_key, because it operates on partitions of data rather than individual rows"*), y **microbatch es una excepción documentada y explícita al comportamiento de `--full-refresh`**: *"running dbt run --full-refresh on a microbatch model by itself won't reset or reload data unless you have a begin datetime config for the model"*, con la recomendación de best-practice de neutralizar el flag: *"we recommend configuring full_refresh: false on microbatch models so that they ignore invocations with the --full-refresh flag."* Esto demuestra que "`--full-refresh` siempre reconstruye toda la tabla" **no es universalmente cierto** — depende de la estrategia incremental configurada.
- El config `full_refresh: true|false|none` a nivel de modelo/proyecto es un override explícito del flag de CLI: `true` fuerza refresh siempre, `false` lo desactiva siempre (caso de uso: microbatch), `none`/omitido sigue el flag de CLI.

**`is_incremental()`:** verificado con fetch independiente. Retorna `True` solo si las tres condiciones se cumplen a la vez: *"The model must already exist as a table in the database"*, *"The full-refresh flag is not passed"*, *"The running model is configured with materialized='incremental'"*. Pasar `--full-refresh` rompe la segunda condición, por lo que el bloque SQL condicionado a `is_incremental()` (típicamente el `WHERE` que filtra filas nuevas/cambiadas) se salta, y el modelo se construye contra el dataset fuente completo — consistente con el drop-and-rebuild ya confirmado arriba.

Fuentes: [Configure incremental models](https://docs.getdbt.com/docs/build/incremental-models) (re-verificado con fetch independiente), [About microbatch incremental models](https://docs.getdbt.com/docs/build/incremental-microbatch), [`full_refresh` config](https://docs.getdbt.com/reference/resource-configs/full_refresh)

## 4. Full reload vs. incremental: ¿hay fuente primaria para la guía "chico → full, grande → incremental"?

**dbt (genérico, sin vocabulario dimensión/hecho):** la "Golden Rule" de la guía de best practices de dbt, verbatim: *"Start with models as views, when they take too long to query, make them tables, when the tables take too long to build, make them incremental."* Y: *"[Incremental models are] particularly useful for large datasets, where the cost of processing the entire dataset is high"*, recomendados cuando *"your dbt runs are becoming too slow."* Esto respalda la lógica general costo/tamaño, pero dbt la enmarca en términos de view→table→incremental, no en vocabulario "dimensión vs. hecho".
Fuentes: [Materializations best practices](https://docs.getdbt.com/best-practices/materializations/5-best-practices), [Available materializations](https://docs.getdbt.com/best-practices/materializations/2-available-materializations)

**Snowflake — la cita primaria más directa encontrada, re-verificada con un segundo fetch independiente para descartar drift de resumen.** De la página oficial "Best practices for dbt Projects on Snowflake", sección "Use incremental models for large, frequently updated tables": *"If your source table is large and receives regular updates, use the incremental materialization instead of a full table rebuild."* Y, la frase que sostiene directamente el lado "chico" de la afirmación: *"For small tables that update infrequently, a full table materialization is simpler and often just as fast."* Esta es, de los seis motores + dbt, la única fuente que hace la afirmación explícita "tablas chicas → full reload, tablas grandes/frecuentes → incremental" con el mismo nivel de generalidad que la pregunta original — aunque fraseada como "large, frequently updated tables", no específicamente "fact tables".
Fuente: [Best practices for dbt Projects on Snowflake](https://docs.snowflake.com/en/user-guide/data-engineering/dbt-projects-on-snowflake-best-practices)

**Snowflake Dynamic Tables — eje relacionado pero distinto (no confundir en el skill).** La guía de refresh modes usa **porcentaje de filas cambiadas**, no tamaño absoluto de la tabla, como criterio: *"Fewer than five percent of the base table data changes between refreshes"* favorece incremental; *"A large fraction of the base table data changes between refreshes, making incremental processing more expensive than a full scan"* favorece full. Nota importante para no mezclar los dos criterios: una tabla de dimensión chica con alta tasa de cambio podría favorecer full refresh por esta lógica, y una tabla de hechos enorme con un delta diario minúsculo favorece incremental — consistente con, pero no idéntico a, el criterio "chico vs. grande" de la pregunta original.
Fuente: [Dynamic table refresh modes](https://docs.snowflake.com/en/user-guide/dynamic-tables/refresh-modes)

**AWS Prescriptive Guidance — soporte parcial, solo lado "chico".** Patrón oficial de AWS para pipelines Glue→Redshift, sección "Detailed approach for upsert and complete refresh": *"Complete refresh: This is for small datasets that don't need historical aggregations"*, contra *"Upsert: This is for datasets that require historical aggregation, depending on the business use case."* Respalda el lado "datasets chicos → full/complete refresh" con autoridad de vendor, pero no dice explícitamente lo simétrico sobre datasets grandes.
Fuente: [Build an ETL service pipeline to load data incrementally from Amazon S3 to Amazon Redshift using AWS Glue](https://docs.aws.amazon.com/prescriptive-guidance/latest/patterns/build-an-etl-service-pipeline-to-load-data-incrementally-from-amazon-s3-to-amazon-redshift-using-aws-glue.html)

**BigQuery — no se encontró respaldo.** La página oficial de control de costos sí recomienda carga incremental (`WRITE_APPEND`/`MERGE`) sobre sobrescribir, pero el argumento es **costo de storage por overwrite frecuente y ventanas de time-travel/failsafe**, no tamaño de tabla: *"If you overwrite a table frequently, you will incur additional storage charges"*; *"When you overwrite a table... the replaced data is kept for the duration of the time travel and failsafe windows."* Flag explícito: no forzar esta cita como respaldo de "tablas chicas → full reload" — el argumento de BigQuery es ortogonal (frecuencia de overwrite, no tamaño).
Fuente: [Estimate and control costs](https://docs.cloud.google.com/bigquery/docs/best-practices-costs)

**Conclusión de la pregunta 4:** la heurística "dimensión/chica → full reload, hecho/grande → incremental" **sí tiene respaldo primario real**, pero concentrado — Snowflake la afirma explícitamente y con generalidad casi idéntica a la pregunta original; dbt y AWS la respaldan parcialmente (dbt en términos de costo/tamaño genérico, AWS solo el lado "chico"); BigQuery no la respalda con la fuente encontrada. No es, contra lo que uno podría asumir, "solo sabiduría de práctica sin fuente primaria" — pero tampoco es una afirmación universal de los seis vendors por igual.

## Resumen de acciones para `engineering-query-patterns.md`

Todo lo anterior queda **confirmado contra documentación oficial**, con los flags de no-verificable anotados explícitamente en cada sección — construir la nueva sección "Full load (truncate-and-reload)" directamente sobre esta base. Puntos a destacar como contenido "senior", en línea con la profundidad ya establecida en el archivo para `MERGE`/SCD Type 2:

1. **TRUNCATE no es un DELETE rápido intercambiable sin pensar** — la matriz de transaccionalidad es genuinamente distinta por motor: PostgreSQL y SQL Server lo hacen rollback-able pese a ser DDL (SQL Server) o casi-DDL (PostgreSQL); MySQL lo prohíbe directamente dentro de una transacción; Snowflake y BigQuery lo tratan como DML rollback-able; **Redshift diverge de su propio ancestro PostgreSQL** y comitea implícitamente — este último es el gotcha con mayor probabilidad de morder a alguien que asume "Redshift ≈ Postgres".
2. **El patrón CTAS+swap tiene un solo motor con un comando propósito-construido y atómico por diseño**: `ALTER TABLE ... SWAP WITH` de Snowflake (*"Swap renames two tables in a single transaction"*). Redshift tiene el segundo respaldo más fuerte, con un patrón nombrado oficialmente ("Performing a deep copy") pero implementado como DROP+RENAME, no como swap de dos renames. Los demás motores tienen las primitivas (CTAS, RENAME) documentadas por separado, sin que el vendor conecte ambas como técnica de reload — evitar presentar el patrón compuesto como igualmente "oficial" en los seis motores.
3. **`dbt --full-refresh` es drop-and-recreate, no truncate-and-reload** — distinción exacta que vale la pena preservar en el skill en vez de simplificarla. Cross-linkea naturalmente con la sección ya existente de idempotencia (`MERGE`) y con SCD Type 2: un full-refresh de un modelo con `unique_key` no usa esa key para nada, porque no hay "matched/not matched" — se reconstruye todo desde cero.
4. **La heurística "dimensión chica → full reload, hecho grande → incremental" tiene respaldo primario real (Snowflake, parcialmente AWS/dbt)** — puede citarse en el skill sin la advertencia de "esto es solo práctica común", pero conviene anotar que no los seis vendors la formulan con el mismo vocabulario (Snowflake habla de "large, frequently updated tables", no de "fact tables" explícitamente).

**Nota de honestidad epistémica** (mismo criterio que en el research de procedural extensions — RBAR, ausencia de guía de cursores en Postgres): los siguientes puntos quedan explícitamente **sin verificar** y no deben presentarse en el skill como hechos citados sin la salvedad correspondiente, o deben omitirse:
- Si `TRUNCATE` resetea el seed de una columna `AUTOINCREMENT`/`IDENTITY` en Snowflake o en Redshift (no encontrado en ninguna doc oficial de ninguno de los dos).
- Si `TRUNCATE TABLE` en BigQuery comparte la cuota de concurrencia de 2 concurrentes/20 en cola documentada para `UPDATE`/`DELETE`/`MERGE` (la doc no lo nombra en esa lista específica).
- La ausencia de columnas identity/auto-increment nativas en BigQuery se infiere por omisión en la sintaxis de `CREATE TABLE`, no por una afirmación explícita de Google.
- El patrón "rename tabla vieja a nombre de respaldo, luego rename tabla nueva al nombre de producción" (sin DROP intermedio) para Redshift no es lo que documenta AWS — AWS documenta DROP+RENAME. Si el skill menciona la variante rename-rename, debe marcarse como adaptación del practicante.
- La clasificación DDL/DML de `TRUNCATE` en Redshift es internamente inconsistente en la propia doc de AWS (aparece en ambas listas en la misma oración de la página de isolation levels) — reportar la ambigüedad tal cual, no resolverla arbitrariamente hacia un lado.
