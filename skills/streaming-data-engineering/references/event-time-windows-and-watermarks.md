# Event Time, Windows, and Watermarks

The previous file drew the line between bounded and unbounded data. This one is about the consequence of that line: once a data set has no defined end, "when did this happen" stops being a single, agreed-upon timestamp and splits into several clocks that disagree with each other by design. Every windowing decision, every watermark setting, and every late-data policy in a stream processor is downstream of getting that split straight first.

## Three times, and why they don't coincide

A single event carries at least three different timestamps, and conflating them is the single most common source of "why is this number wrong" in a streaming pipeline:

- **Event time** — when the thing actually happened: the moment a customer tapped "buy," the moment a sensor read a temperature, the moment a page view fired. Usually generated by the producer, embedded in the payload, and never changes once written.
- **Processing time** — when the stream processor's operator actually handles the record: whenever the CPU gets to it. A property of your system's current load, not of the event.
- **Ingestion time** — when the event entered the messaging system (for example, when it was appended to a Kafka partition). It sits between the other two, and is a reasonable substitute for event time only when the producer couldn't attach one, or the gap between "happened" and "appended" is known to be small and stable.

In a diagram, these three line up. In production, they don't, and the gap between them isn't a bug to be fixed — it's the normal operating condition of any real system. A phone loses signal in a tunnel and its buffered taps arrive fifteen minutes late, all at once, the moment it reconnects. A consumer group rebalances — the mechanic covered in [`the-log-and-partitioning.md`](the-log-and-partitioning.md) — and everything assigned to the reassigned partitions pauses mid-stream while ownership moves. A network path gets congested and a batch of otherwise-timely events queues up somewhere in transit. None of these are exotic failure modes; they're what "unbounded, real-world data" means in practice. Events arrive out of order, and some arrive late enough that the processor has already moved past the point in time they belong to. Windowing and watermarking exist to give you a principled way to handle that, instead of pretending it won't happen.

## Why event time is what you want, even though it costs you

Here is the argument, stated as plainly as it deserves: **if you count by processing time, the answer you get depends on how fast your system happened to be running, not on what actually occurred.** Replay the exact same input through a system under heavier load, or through a consumer that started five minutes late, or through a reprocessing job recovering from an outage, and a processing-time count of "events per minute" or "revenue per hour" comes out different every time — not because the underlying facts changed, but because the clock used to bucket them was your infrastructure's clock, not the world's.

Event time doesn't have that problem. "How many orders happened between 2:00 and 2:05 pm" is a question about the world, and its answer doesn't move depending on when your cluster got around to processing each order. Run the same input through a fast pipeline, a slow one, or a pipeline that crashed and reprocessed the backlog three hours later, and an event-time-windowed result is the same result every time. That's what "correct and reproducible" means here, and it's the property that makes a pipeline testable, auditable, and safe to replay — precisely the guarantee a processing-time bucket can never give you.

The cost is real, and it's the rest of this file: to group by event time, you have to wait for events to arrive, and "waiting" means deciding how long is long enough before calling a window complete — exactly the decision a watermark encodes. Event time buys correctness; the price is latency and the bookkeeping needed to handle stragglers. That trade is not a flaw in the model — it's the model doing its job.

## The batch-shaped version of the same problem

This isn't a problem unique to streaming engines; streaming just makes it mechanical and continuous. A nightly batch job reconciling "yesterday's" activity answers the same question a watermark answers — has enough time passed to call this window done — just once, by a human picking a run time, instead of continuously, by an engine tracking observed event time.

Two places elsewhere in this skill suite name this same problem from the batch side. When a fact record shows up late relative to its own business date, the dimension it needs to join against has usually moved on to a newer version — the late-arriving-facts case in [`scd-and-dimension-patterns.md`](../../modeling-data-engineering/references/scd-and-dimension-patterns.md#late-arriving-dimensions-and-facts), which requires searching Type 2 history for the dimension row in effect when the late event occurred, not the row current today. And the standard batch remedy is what [`idempotency-and-backfills.md`](../../pipelines-architecture-data-engineering/references/idempotency-and-backfills.md#late-arriving-data) describes: reprocess the affected window once delayed data shows up, correct only because the DAG is structurally idempotent and parameterized by its data interval. A watermark is that same reprocessing decision, collapsed into a continuously evaluated engine setting instead of a scheduled rerun.

## Window types: what each one groups, and why

A window turns an unbounded stream into something you can aggregate: a finite slice of event time to sum, count, or average, instead of aggregating "everything, forever."

- **Tumbling windows** are fixed-size, non-overlapping, contiguous slices of event time — every event belongs to exactly one window. "Orders per 5-minute interval" is a tumbling window: [12:00, 12:05), [12:05, 12:10), and so on. The default shape for periodic rollups where every event needs a home and none should be counted twice.
- **Sliding (hopping) windows** are fixed-size but overlapping: a new window starts on a cadence shorter than the window's length, so one event can land in several windows at once. "A rolling 10-minute average, recomputed every minute" is a sliding window. The shape for smoothed, frequently-refreshed metrics where overlap is wanted on purpose.
- **Session windows** have no fixed size — they're defined by a gap of inactivity. A session stays open as long as events keep arriving within some threshold of each other, closing the moment that gap is exceeded. The natural shape for a burst of activity with unknown, variable duration: a browsing session, a device's active period, a sequence of retries.

Session windows are worth pausing on, because the concept isn't specific to a streaming engine — the same grouping logic already exists at the SQL layer. [`engineering-query-patterns.md`](../../sql-data-engineering/references/engineering-query-patterns.md#sessionization) builds sessions by hand with `LAG` (measuring the gap since the previous event) and a running `SUM` over a `ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW` frame to assign a session id. A streaming engine's session window does the same grouping — close on inactivity past a threshold — as a first-class primitive instead of a hand-rolled window function. If you already understand why the SQL version needs an explicit `ROWS` frame instead of the implicit `RANGE` default (to avoid two events tied on timestamp merging into the wrong session), you already understand the edge case a streaming session window handles internally too.

Windows answer one of the two questions this file builds toward: *where in event time is data grouped together.* They say nothing yet about *when* a window's result gets emitted — that's covered after watermarks are on the table, and again at the end under triggers.

## Completeness is an estimate, not a fact — and the watermark is that estimate, made mechanical

In a batch job, "have I seen everything for 2–3 pm" has a real, checkable answer: the job reads a bounded partition, so once the read finishes, the answer is yes, by construction. There is no such answer in a streaming system. However long you wait, one more straggler event — the phone that just came out of the tunnel, the retry that finally got through congestion — is always structurally possible. "All the 2–3 pm events have arrived" is never a fact you can verify in an unbounded stream; it's a bet you're forced to make, since refusing to make it means never emitting a result for 2–3 pm at all.

That's what a watermark actually is: the bet, made mechanical. A watermark is an engine-tracked estimate of event-time progress — typically the maximum event timestamp observed so far, minus a configured tolerance — that lets the engine say "I am now willing to treat this point in event time as done," fully aware the statement is a probabilistic judgment, not a guaranteed fact. Flink's documentation states the guarantee in terms worth preserving exactly, because the boundary condition matters: "A Watermark(t) declares that event time has reached time t in that stream, meaning that there should be no more elements from the stream with a timestamp t' <= t (i.e. events with timestamps older or equal to the watermark)" (Apache Flink documentation, stable/v2.3.0, "Notions of Time"). The comparison is `<=`, not `<` — a watermark of `t` covers events timestamped exactly at `t`, not just strictly before it.

That single conceptual step — completeness in streaming is an estimate a watermark encodes, not a fact a bounded read confirms — separates someone who configures a delay because a tutorial said 10 minutes from someone who can reason about what the setting is betting on. The number isn't a technical constant; it's a claim about how late the worst-case straggler is likely to be.

## The watermark trade: there is no universally correct setting

Because a watermark is a bet rather than a fact, every watermark configuration is a trade along the same axis, and the two ends of that axis have opposite failure modes:

- **An aggressive (short) watermark delay** closes windows quickly — low latency, exactly what a downstream consumer needing an answer soon wants. The cost: more late-arriving events fall past the watermark and land in whatever "too late" handling is configured, rather than the aggregate they logically belong to.
- **A conservative (long) watermark delay** waits longer before calling a window done — more complete, fewer stragglers excluded — at the cost of higher latency (the 2–3 pm answer doesn't materialize until well after 3 pm) and more retained state, because the engine keeps every open window's intermediate counts around as long as it's still willing to accept updates.

There is no setting that wins on all three axes at once, and no context-free "correct" watermark delay — the number only makes sense against a stated business requirement. A fraud-scoring pipeline that has to block a transaction before it clears has no room for a 10-minute watermark, whatever completeness it sacrifices — the latency budget is the binding constraint, and a short delay is the only tenable answer. A billing reconciliation pipeline computing hourly revenue has the opposite priority: correctness matters more than shaving minutes off latency, so a longer delay tolerating known device-offline patterns is the right call, even though it means holding more state and reporting later. The senior judgment isn't "know the trade exists" — it's naming the number the business actually needs and picking the delay that serves it, rather than defaulting to whatever value a tutorial used.

## What happens to data that arrives after the watermark has passed

Once a watermark advances past a window's end, an engine has to decide what to do with any record still arriving for that window. There are three real options, not one:

1. **Drop it.** The default in engines like Flink: "By default, late elements are dropped when the watermark is past the end of the window" (Apache Flink documentation, stable/v2.3.0, "Allowed Lateness"). Correct when the cost of missing a straggler is genuinely negligible.
2. **Allowed lateness, with an updated result.** Flink lets you configure a grace period past the watermark during which late elements are still incorporated, and a late-but-accepted element can cause the window to fire again with a revised result: "Allowed lateness specifies by how much time elements can be late before they are dropped, and its default value is 0. Elements that arrive after the watermark has passed the end of the window but before it passes the end of the window plus the allowed lateness, are still added to the window. Depending on the trigger used, a late but not dropped element may cause the window to fire again... In order to make this work, Flink keeps the state of windows until their allowed lateness expires" (Apache Flink documentation, stable/v2.3.0, "Allowed Lateness"). The default is zero — "allow lateness and revise the result" is opt-in, and choosing it means accepting more retained state for longer, the same trade covered above.
3. **Route it somewhere inspectable.** Rather than silently discarding a too-late record or forcing it into a closed window's result, send it to a separate output stream or table — the same shape as the quarantine pattern in [`failure-response-policies.md`](../../quality-data-engineering/references/failure-response-policies.md#quarantine-mark-dont-silently-drop): don't silently drop, mark and divert somewhere inspectable, so a human or downstream job can decide whether the straggler still matters. A too-late record isn't necessarily worthless — it might land in an audit table, correct an already-published report, or feed SLA monitoring on pipeline lateness.

Which of the three is right depends on the same calibration as the watermark delay itself: how much does a missed straggler actually cost.

## Spark Structured Streaming's actual behavior — and why "late data is dropped" is not a safe blanket statement

A phrase repeated often enough to sound like settled fact is "Structured Streaming drops late data." Spark's own documentation (version 4.2.0) does not support that as a universal claim, and the distinction it draws is specifically by **output mode** — stating this without naming the mode is actively misleading.

**In Complete mode, watermarking cannot drop anything, because there is nothing it's allowed to drop.** Complete mode's contract is to re-emit the full result table on every trigger, so it has to retain every aggregate it's ever computed. Spark's documentation states the precondition for watermark-driven cleanup explicitly: "Output mode must be Append or Update. Complete mode requires all aggregate data to be preserved, and hence cannot use watermarking to drop intermediate state" (Apache Spark documentation, 4.2.0, "Conditions for watermarking to clean aggregation state"). In Complete mode, a watermark does no late-data filtering at all — it literally cannot, because the mode requires everything preserved.

**In Append and Update mode, the guarantee is real but one-directional, and it does not say what the popular paraphrase claims.** The documentation states it this way: "A watermark delay... of '2 hours' guarantees that the engine will never drop any data that is less than 2 hours delayed. In other words, any data less than 2 hours behind (in terms of event-time) the latest data processed till then is guaranteed to be aggregated. However, the guarantee is strict only in one direction. Data delayed by more than 2 hours is not guaranteed to be dropped; it may or may not get aggregated. More delayed is the data, less likely is the engine going to process it" (Apache Spark documentation, 4.2.0, "Semantic Guarantees of Aggregation with Watermarking"). The only thing Spark formally guarantees is that data *within* the delay is **not lost**; it explicitly does **not** guarantee data *beyond* it is dropped — it may or may not get aggregated. The popular one-liner inverts the one guarantee Spark actually makes.

What's mechanically happening in Append/Update mode is that watermarking releases **intermediate state**, not that it inspects and discards each late record individually. In Update mode: "when the watermark is updated to 12:11, the intermediate state for window (12:00 - 12:10) is cleared, and all subsequent data... is considered 'too late' and therefore ignored" (Apache Spark documentation, 4.2.0, watermarking example). In Append mode, the engine waits out the full delay before ever emitting a result: "the engine maintains intermediate counts for each window... The engine waits for '10 mins' for late date to be counted, then drops intermediate state of a window < watermark, and appends the final counts to the Result Table/sink" (same source). In both modes, a record arriving after its window's state has been released has nothing left to aggregate into — ignored as a side effect of the state being gone, not the engine detecting and discarding that specific record. **The wording to carry forward: Structured Streaming guarantees data within the watermark delay is not lost, and explicitly does not guarantee data beyond it is dropped — never that late data is unconditionally dropped, and never without naming the output mode.**

Spark also ships a **Continuous Processing** mode aiming at ~1ms latency instead of the micro-batch default's ~100ms. As of the 4.2.0 documentation it's still marked "[Experimental]," and the surrounding text still reads "As of Spark 2.4, only the following type of queries are supported in the continuous processing mode" — unrevised for any version after 2.4, several major releases ago. Treat it as the documentation shows it: experimental and stalled, not an actively developed alternative to plan around.

## Triggers, and the frame that ties all of this together

Everything above answers *where* in event time data gets grouped (windows) and *how completeness gets estimated* (watermarks). One question is still open: *when*, in processing time, does a result actually get emitted? That's what a **trigger** decides, and it's a genuinely separate axis from windowing. The paper that formalized this area states the separation directly: "triggers are a mechanism for stimulating the production of... results in response to internal or external signals. They are complementary to the windowing model, in that they each affect system behaviour along a different axis of time: Windowing determines where in event time data are grouped together for processing. Triggering determines when in processing time the results of groupings are emitted as panes" (Akidau et al., "The Dataflow Model," VLDB 2015, p. 1797). A watermark crossing a window's boundary is one common trigger condition, but not the only one — a count of elements, a processing-time timer, or an early "speculative" fire before the watermark arrives are all valid, layered on the same windowing decision.

Put windows, watermarks, and triggers together and you have the four questions the same paper uses to decompose any streaming (or batch) pipeline, verbatim: "What results are being computed. Where in event time they are being computed. When in processing time they are materialized. How earlier results relate to later refinements" (Akidau et al., "The Dataflow Model," VLDB 2015, p. 1793). Windowing answers *where*; watermarks and triggers together answer *when*. This file has built vocabulary for exactly those two questions, because everything above depends on them: without event time and windows, "where" has no meaning; without watermarks as an estimate of completeness, "when" has no principled trigger condition to fire on. *What* is computed and *how* refinements relate (whether a revised result replaces, retracts, or accumulates alongside an earlier one) are the remaining two questions, and the ground the next files in this skill build on — using this file's watermark and window vocabulary as the thing state and delivery guarantees, deduplication, and windowed joins get calibrated against.

## Common mistakes

| Mistake | Why it hurts | Fix |
|---|---|---|
| Aggregating by processing time and calling the result "the count" | The number depends on system speed, so replaying identical input produces a different answer | Aggregate by event time; accept latency and straggler-handling as the price of reproducibility |
| Treating "have all the events for this window arrived" as checkable | Streaming has no bounded read to confirm against — one more straggler is always possible | Treat completeness as an estimate a watermark encodes, calibrated to what a missed straggler costs |
| Copying a watermark delay from another pipeline without stating the requirement it serves | A delay tuned for one latency/completeness trade-off is likely wrong for a different requirement | Name the actual SLA or late-data tolerance first, then set the delay to match it |
| Writing "Structured Streaming drops late data" as a blanket claim | Complete mode can't drop state via watermarking at all; in Append/Update mode, Spark guarantees only that data *within* the delay is not lost, and explicitly does not guarantee data beyond it is dropped | Name the output mode, and state the one-directional guarantee Spark actually documents |
| Assuming a late record is gone the moment it misses its window | It may instead trigger allowed lateness or get routed to a separate inspectable output — "gone" is one of several outcomes | Check which policy — drop, allowed lateness, or route somewhere inspectable — is actually configured |
| Reaching for Continuous Processing because ~1ms beats ~100ms | Still `[Experimental]` in Spark 4.2.0, with no substantive documentation update since 2.3/2.4 — stalled, not actively developed | Default to micro-batch; treat Continuous Processing as unproven for production |
