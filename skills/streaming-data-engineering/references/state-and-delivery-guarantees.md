# State, Checkpointing, and Delivery Guarantees

Every prior file in this skill treats a stream processor as something that transforms events as they pass through. This one is about what happens when the processor has to *remember* something across events — a running count, the last watermark seen, a half-built session — and about the honest scope of the guarantee an engine can actually give you once that memory has to survive a crash.

## Stateful vs. stateless, and why state is the hard part

A stateless operation reads one event, produces zero or more output events, and forgets everything the moment it's done. A filter, a map, a field-level transform — none of them need to remember event N when event N+1 arrives. That's the easy case, and it's most of what a batch job does too: run the transform, discard the intermediate, move on.

A stateful operation is different in a way that matters more in streaming than it ever does in batch: a count-per-key, a running sum, a join buffer waiting for its other side, a deduplication set of recently-seen IDs — all of these need the result of processing event N to still be there when event N+1 shows up, possibly seconds later, possibly after the process that held it has crashed and restarted somewhere else. In a batch job, state is cheap to reason about because it dies with the job: the job starts, accumulates whatever it needs in memory, finishes, and the state is gone — there was never a requirement that it outlive the run, because the run has a defined end. In streaming there is no defined end (the distinction [`unbounded-data-and-when-not-to-stream.md`](unbounded-data-and-when-not-to-stream.md) establishes for this whole skill), which means the state a job accumulates has nowhere to go — it has to be long-lived, it has to survive process failure without disappearing, and it has to be something the engine can hand off cleanly when work moves to a different machine after a rebalance or a restart.

That same unboundedness creates a second problem state-in-batch never has: state cannot simply keep growing forever, because "forever" is the actual lifetime of the input. A per-key count with no bound on how many keys ever appear, or a join buffer holding every unmatched event since the job started, eventually exhausts whatever memory or disk backs it — not eventually in an abstract sense, but eventually on a timeline you can calculate from ingest rate and available capacity. This is exactly why windows and watermarks — covered in [`event-time-windows-and-watermarks.md`](event-time-windows-and-watermarks.md) — exist as more than a way to group events for aggregation: a window's close, once the watermark has passed it, is also the signal that the state backing that window can be released. State-with-TTL is the general form of the same idea: keep it as long as it's still needed to answer a question correctly, and no longer, because "no longer" is the only thing standing between a stateful job and unbounded growth on an unbounded stream.

## State backends: where the memory actually lives

An engine has to store that long-lived state somewhere, and the choice of *where* is a real operational decision, not an implementation detail to ignore. Apache Flink documents two backends with genuinely different failure modes. Flink's own documentation is explicit about which one you get without configuring anything: "If nothing else is configured, the system will use the HashMapStateBackend." That backend "holds data internally as objects on the Java heap" — fast, because nothing has to be serialized on the way in or out, but bounded by however much memory the task manager has, and a bad choice the moment state size approaches or exceeds available RAM.

The alternative is embedded RocksDB. Flink's documentation is explicit that `EmbeddedRocksDBStateBackend` "holds in-flight data in a RocksDB database that is (per default) stored in the TaskManager local data directories," runs embedded inside the TaskManager process rather than as a separate service, and is "encouraged for: Jobs with very large state, long windows, large key/value states." The load-bearing sentence is the one about the actual limit: "the amount of state that you can keep is only limited by the amount of disk space available. This allows keeping very large state, compared to the HashMapStateBackend that keeps state in memory." The same page draws the serialization contrast explicitly: "Unlike storing java objects in `HashMapStateBackend`, data is stored as serialized byte arrays," which is exactly why "the maximum throughput that can be achieved will be lower with this state backend." Trading heap for disk costs serialization overhead on every read and write, but it turns "will this job run out of memory" into "will this job run out of disk" — a much larger and much more predictable budget for a job with large keyspaces, long windows, or session state that can't be evicted quickly. The choice between the two backends is the same shape as the choice between `HashMapStateBackend`'s speed and RocksDB's capacity, and it should be made deliberately from expected state size, not left at whatever the project template shipped with.

## Checkpointing: fault tolerance for state, and why it needs a replayable source

Long-lived state is only useful if it survives the failure it was built to outlast. Checkpointing is the mechanism that makes that true: a distributed, consistent snapshot of every operator's state, taken while the stream keeps moving, that the job can restore from after a crash instead of starting over from nothing.

Flink's documentation describes the mechanism precisely, and the precision is worth carrying into the skill because it explains why the snapshot is *consistent* rather than a haphazard collection of per-operator dumps: "Flink uses a variant of the Chandy-Lamport algorithm known as asynchronous barrier snapshotting. When a task manager is instructed by the checkpoint coordinator... to begin a checkpoint, it has all of the sources record their offsets and insert numbered checkpoint barriers into their streams. These barriers flow through the job graph, indicating the part of the stream before and after each checkpoint. Checkpoint n will contain the state of each operator that resulted from having consumed every event before checkpoint barrier n, and none of the events after it." Operators with two input streams perform barrier alignment, waiting for the barrier on both inputs before snapshotting, so the recorded state reflects a single, agreed point across the whole job graph rather than each operator's own arbitrary moment. And the snapshot doesn't stop the world to take itself: "Flink's state backends use a copy-on-write mechanism to allow stream processing to continue unimpeded while older versions of the state are being asynchronously snapshotted."

Restore is the mirror image of that snapshot: on recovery, every operator's state is reloaded from the most recent completed checkpoint, and — because the sources recorded their offsets as part of that same checkpoint — the job resumes reading from exactly the point in each source that corresponds to the restored state, not from wherever the source happens to be now.

That last clause is where checkpointing stops being a self-contained fact about the engine and becomes dependent on something outside it. A restored checkpoint tells the job "your state was correct as of source offset X." That statement is only useful if the source can actually be re-read starting at offset X. [`the-log-and-partitioning.md`](the-log-and-partitioning.md#replayability-the-property-that-makes-recovery-reprocessing-and-kappa-possible) already established why a Kafka log lets a consumer "deliberately rewind back to an old offset and re-consume data" — that's the mechanism, and it doesn't need re-deriving here. What's worth making explicit at this point is *why* it's a precondition rather than a nice-to-have: without a source that can rewind, a restored checkpoint has a consistent memory of "where we were" and nothing consistent to resume reading from — the state says offset X, but the source has already moved on and discarded what was at X, or never supported rewinding in the first place. Flink's own connector documentation states this dependency as a hard requirement, not a recommendation: "Flink can guarantee exactly-once state updates to user-defined state only when the source participates in the snapshotting mechanism." A checkpoint without a replayable source underneath it is a snapshot of state with no way to prove, or restore, that the state and the input are still in agreement.

## The three delivery semantics

Every message a processor moves from a source to a sink lands somewhere on a spectrum of three possible guarantees, and it's worth naming all three before focusing on the one everyone asks about:

- **At-most-once** — a message is delivered zero or one times. Nothing is retried after a failure, so a crash between reading and processing a record simply loses it. Cheap and fast, and rarely the right default for anything with a correctness requirement.
- **At-least-once** — a message is delivered one or more times. Nothing is ever silently lost, but retries after a failure can redeliver something already processed, producing duplicates unless something downstream removes them. This is the default posture most streaming systems land on once they retry anything at all, and it's the same guarantee webhooks give on the ingestion side: [`external-api-integration.md`](../../python-data-engineering/references/external-api-integration.md#push-vs-pull-webhooks-and-bulk-export) documents that webhook deliveries are "typically **at-least-once**," citing Stripe's own warning that "webhook endpoints might occasionally receive the same event more than once." Flink's own connector guarantee table backs the "common default" framing directly: several of its sinks — a Kafka producer, a Cassandra sink — are documented as "at least once" out of the box, with "exactly once" available only as an additional, narrower condition (transactional producers for Kafka, idempotent updates for Cassandra). At-least-once isn't the fallback when exactly-once configuration is missing; it's the baseline every one of these systems starts from.
- **Exactly-once** — the guarantee everyone wants and the one worth being careful about, covered next.

## What "exactly-once" actually means — and where it breaks

The first thing to get right about exactly-once is what the term is *not* claiming, because engines themselves are careful about this even when the marketing around them isn't. Flink's own fault-tolerance documentation states the distinction directly: "when the ideal situation is described as exactly once this does not mean that every event will be processed exactly once. Instead, it means that every event will affect the state being managed by Flink exactly once." Its connector documentation draws the same line in different words: "To guarantee end-to-end exactly-once record delivery (**in addition to exactly-once state semantics**), the data sink needs to take part in the checkpointing mechanism." Read those two together and the shape of the hedge is clear — Flink's checkpointing gives you **exactly-once state semantics**: a guarantee that Flink's own internal, checkpointed state reflects each event exactly once. That is a real and valuable guarantee, and it is not the same statement as "each record is physically delivered to the outside world exactly once." The second statement needs more than the engine's internal consistency; it needs the sink's cooperation too.

Kafka's documentation makes essentially the same warning from the producer/consumer side, in its own words rather than Flink's: "Many systems claim to provide 'exactly-once' delivery semantics, but it is important to read the fine print, because sometimes these claims are misleading (i.e. they don't translate to the case where consumers or producers can fail, cases where there are multiple consumer processes, or cases where data written to disk can be lost)." Two different projects, two different vocabularies, the same instruction: don't take an "exactly-once" label at face value without checking what specifically it covers.

That's the substance behind this file's central argument: **exactly-once is not a switch you flip in a configuration file. It is an end-to-end property, and it requires all three of the following at once:**

1. **A replayable source** — established above, and in [`the-log-and-partitioning.md`](the-log-and-partitioning.md#replayability-the-property-that-makes-recovery-reprocessing-and-kappa-possible): without the ability to rewind, a restored checkpoint has nothing consistent to resume from.
2. **Checkpointed state** — the mechanism this file has just walked through: a consistent, restorable snapshot of what the job has done with the input so far.
3. **An idempotent or transactional sink** — covered next: something on the output side that either tolerates being written to twice, or participates in the same all-or-nothing commit as the checkpoint.

Flink's own connector guarantee table is where this stops being an abstraction: it lists source connectors with different guarantees side by side — Kafka sources documented as "exactly once," Google PubSub as "at least once," plain sockets as "at most once" — and sink connectors the same way, with a Kafka producer moving from "at least once" to "exactly once" only "with transactional producers," and a Cassandra sink reaching "exactly once" only "for idempotent updates." Two separate tables, two separate sets of guarantees, and nothing that lets a sink's configuration compensate for a source that can't replay, or a source's replayability compensate for a sink that overwrites blindly. The chain is exactly as strong as its weakest link — the individual requirements (replayable source, checkpointed state, cooperating sink) are each independently documented, but the "weakest link" framing itself is this skill's synthesis of that structure, not a sentence lifted from either project's documentation, and it's worth being honest about that distinction rather than dressing a reasonable inference up as a quote.

Make the failure case concrete, because this is the part a reader should be able to apply to a pipeline they're actually looking at: if the sink is a call to an external API with no idempotency key on the request, a retry after a checkpoint restore sends that call again, and the receiving system has no way to tell "this is the retry of a call that already succeeded" from "this is a new call." If the sink is a blind append to a file or an `INSERT`-only table, a reprocessed batch after a restore adds duplicate rows, full stop — there's no mechanism on the write side that would even notice the duplication, let alone prevent it. In both cases, the engine did its part exactly as documented — the checkpoint was consistent, the state was correct — and the pipeline still isn't exactly-once end to end, because the third link never existed. A reader looking at a proposed pipeline should be able to point at exactly one of the three links — source, state, sink — and say "this one is missing," rather than treating "does the engine support exactly-once" as a single yes/no question about the processing framework alone.

## How a sink actually gets there: transactions or idempotency by key

There are two documented mechanisms by which a sink earns its place as the third link, and they solve the problem differently.

**Transactional, atomic commit.** Kafka's transactional producer, available since 0.11.0.0, makes the write itself atomic across partitions: "the producer supports the ability to send messages atomically to multiple topic partitions using transactions, so that either all messages are successfully written or none of them are." The part that matters most for a read-process-write pipeline is what else rides inside that same transaction: "The consumer's position is stored as a message in an internal topic, so we can write the offset to Kafka in the same transaction as the output topics receiving the processed data. If the transaction is aborted, the consumer's stored position will revert to its old value... and the produced data on the output topics will not be visible to other consumers" under the `read_committed` isolation level. That's the mechanism in one sentence: the offset commit and the output write are the same atomic operation, so a crash between the two is impossible by construction — either both happened, or neither did, and a downstream reader in `read_committed` mode never sees the partial case either way. That's the same all-or-nothing property checkpointing gives the processing side — a checkpoint either captured a consistent state across the whole job graph or it didn't, with nothing partial left behind — extended one hop further so it now covers the sink's commit too. The two are related by that shared atomicity property, not by sharing a mechanism: checkpointing coordinates through barriers flowing through the job graph, not through a two-phase commit protocol, and the two shouldn't be conflated just because both end up all-or-nothing.

**Idempotency by key.** Where a transactional protocol isn't available or isn't the right tool, the alternative is a sink that tolerates being written to more than once because the write is keyed and self-correcting rather than append-only. This is exactly the mechanism [`engineering-query-patterns.md`](../../sql-data-engineering/references/engineering-query-patterns.md#idempotent-upserts-with-merge) teaches as `MERGE`/upsert — re-running the same write against the same key updates what already exists instead of duplicating it — and the `ROW_NUMBER()`-based deduplication in the same file's [deduplication section](../../sql-data-engineering/references/engineering-query-patterns.md#deduplication-canonical-form) for collapsing duplicates that already made it into a table before a key-based upsert was in place. Neither mechanism is re-taught here; both are the SQL-level implementation of the same idempotent-sink requirement this file has been arguing for at the architecture level. A stream processor writing to a sink that supports `MERGE` on a natural key, or that runs a periodic `ROW_NUMBER()` pass to collapse whatever duplicates a retry produced, has satisfied the third link without needing a transactional protocol at all.

## The idempotency thread, closed

Idempotency has been a recurring concern across this entire skill suite, and this is the file where it stops being a local best practice and becomes the condition an end-to-end correctness argument depends on. It's worth tracing the whole thread in one place:

- It starts at the function level, in [`production-patterns.md`](../../python-data-engineering/references/production-patterns.md#idempotency-and-safe-reruns): "overwrite-or-merge by partition/key, never blind append," so that re-running a task for the same logical partition produces the same end state rather than a duplicate.
- It becomes a structural property of the DAG itself in [`idempotency-and-backfills.md`](../../pipelines-architecture-data-engineering/references/idempotency-and-backfills.md#structural-idempotency-the-window-parameterized-task): each run tied to a data interval, writing that interval's partition with an overwrite rather than an append, so a rerun and a backfill are both safe by construction rather than by discipline.
- It shows up again on the ingestion side as the reason webhook receivers can't be naive: [`external-api-integration.md`](../../python-data-engineering/references/external-api-integration.md#push-vs-pull-webhooks-and-bulk-export) documents webhook delivery as at-least-once and instructs receivers to "design your receiver to be idempotent on the event ID from day one," because the provider's own retries guarantee duplicates will arrive eventually, not exceptionally.
- And here, it becomes the third and usually weakest link in an end-to-end exactly-once claim: no amount of checkpoint consistency on the processing side substitutes for a sink that can absorb a duplicate write without corrupting the result.

Every one of those is the same principle applied at a different layer — function, DAG, HTTP receiver, streaming sink — and the reason it recurs this often is not repetition for its own sake. Idempotency is the property that turns "this failed and we don't know what state it left things in" into "we ran it again and that's fine," and a system built without it anywhere in the chain has no safe way to recover from the failures that will, eventually, happen. Exactly-once delivery is simply what that same property is called once it's the sink's job in a streaming pipeline rather than a batch task's.

## Common mistakes

| Mistake | Why it hurts | Fix |
|---|---|---|
| Treating "exactly-once" as a single processing-framework setting | The engine's checkpointing only guarantees exactly-once *state* semantics; end-to-end delivery also needs a replayable source and a cooperating sink | Check all three links — source, state, sink — before claiming exactly-once for a pipeline, not just the engine's configuration page |
| Pointing an exactly-once-configured engine at a sink with no idempotency key and no transaction support | The engine did its job; a retry after a checkpoint restore still produces a duplicate write the sink has no way to detect | Add a natural key and an upsert/`MERGE` path, or use a transactional sink, before calling the pipeline exactly-once |
| Choosing the default in-memory state backend for a job with large or long-lived keyspaces | `HashMapStateBackend` is bounded by task-manager heap; large state runs out of memory well before it runs out of business value | Move to `EmbeddedRocksDBStateBackend` when state size approaches available RAM — the limit becomes disk, not heap |
| Assuming at-least-once means "duplicates are rare" | At-least-once is the *default* posture of most retrying systems — Kafka producers, Cassandra sinks, webhook senders — not an edge case that occasionally fires | Design every consumer of an at-least-once source to be idempotent from the start, the same discipline webhook receivers need |
| Quoting "fails at the weakest link," or any informal hedge-word coinage circulating around exactly-once, as if it were a direct quote from Kafka or Flink | These phrases don't appear in either project's current documentation, even though a version of one circulates widely in secondary sources | State the synthesis as your own reasoning, and use Flink's actual term — "exactly-once state semantics" — when the state/delivery distinction needs a citable name |
