# Streaming Architecture and Engines

Every other file in this skill answers a question inside an already-chosen pipeline: how to window, how to guarantee delivery, how to join a stream against a table. This file answers the question that comes before all of them: what shape does the pipeline itself take, and what do you run it on. Get here only after [`unbounded-data-and-when-not-to-stream.md`](unbounded-data-and-when-not-to-stream.md) has done its job — this file assumes streaming has already been justified by a real latency requirement, not chosen by reflex.

## Lambda: two pipelines, one obligation they can't escape

The Lambda Architecture, as it was actually practiced, runs two independent code paths against the same data: a **batch layer** that recomputes correct results from scratch over the full historical dataset on a schedule, and a **speed layer** that produces approximate, low-latency results over only the recent window, compensating for the batch layer's lag. A **serving layer** merges the two so a query gets the speed layer's fresh-but-approximate answer for recent data and the batch layer's slow-but-correct answer for everything older.

The architecture's real cost isn't the extra infrastructure — it's the obligation that infrastructure creates. Two systems, usually built on entirely different frameworks (a Hadoop batch job and a Storm or Samza streaming job, in the era the pattern was named), have to implement the *same business logic* twice, in two different programming models, and produce answers that agree at the boundary where the speed layer's window ends and the batch layer's recomputation takes over. Jay Kreps, writing the article that later work in this area treats as the founding text, states the cost plainly: "maintaining code that needs to produce the same result in two complex distributed systems is exactly as painful as it seems like it would be. I don't think this problem is fixable." He adds that the operational complexity this produces "is the one thing that seems to be universally agreed on by everyone doing it" (Kreps, "Questioning the Lambda Architecture," O'Reilly Radar, 2014-07-02). That's the specific failure mode worth carrying forward: not "Lambda is complicated" as a vague complaint, but two logics, written twice, that must never quietly drift apart — and the drift is exactly the kind of bug that only shows up when the two layers' outputs are compared, which is rarely, because comparing them is itself extra work nobody budgeted for.

## Kappa, as Kreps actually proposed it

The same article proposes an alternative: run one streaming pipeline, and when the logic needs to change or a bug needs correcting, reprocess by replaying the log from an earlier offset instead of maintaining a second, separate batch system to do the reprocessing. Kreps's own description of the mechanism is a four-step recipe, and it depends on nothing more exotic than the log replay this skill's earlier file already established:

> "So, how can we do the reprocessing directly from our stream processing job? My preferred approach is actually stupidly simple:
> 1. Use Kafka or some other system that will let you retain the full log of the data you want to be able to reprocess and that allows for multiple subscribers. For example, if you want to reprocess up to 30 days of data, set your retention in Kafka to 30 days.
> 2. When you want to do the reprocessing, start a second instance of your stream processing job that starts processing from the beginning of the retained data, but direct this output data to a new output table.
> 3. When the second job has caught up, switch the application to read from the new table.
> 4. Stop the old version of the job, and delete the old output table."

(Kreps, "Questioning the Lambda Architecture," O'Reilly Radar, 2014-07-02, section "An alternative," quoted in full because the mechanism is the whole point: nothing here needs a second framework, only a second run of the same one.) The mechanism this leans on — a consumer can "deliberately rewind back to an old offset and re-consume data," which "violates the common contract of a queue, but turns out to be an essential feature" — is the exact replayability property [`the-log-and-partitioning.md`](the-log-and-partitioning.md#replayability-the-property-that-makes-recovery-reprocessing-and-kappa-possible) already named and built the argument for. Kappa doesn't introduce a new capability; it's what you get for free once you've accepted that the log is the durable system of record and everything downstream is a rebuildable projection of it.

Kreps himself coined the name in this article, and did so with a shrug rather than a manifesto: "Maybe we could call this the Kappa Architecture, though it may be too simple of an idea to merit a Greek letter" (same source). That tone matters, because it's the opposite of how the idea usually gets repeated. **The claim that circulates today — "Kappa replaces the batch layer entirely" — is a later simplification, not what Kreps wrote.** The word "replace" does not appear anywhere in the original article. Twice over, Kreps hedges in the other direction: he explicitly preserves a place for HDFS and batch processing ("this doesn't mean your data can't go to HDFS; it just means that you don't run your reprocessing there"), and he closes the piece by framing the proposal as conditional, not categorical — "in cases where simplicity is important, consider this approach as an alternative to the Lambda Architecture" (same source, emphasis on "alternative" and "consider"). What Kappa actually eliminates is the need for a *second, separate system* to do reprocessing — not batch processing as a category, and not HDFS as a destination for other uses like ad hoc analysis in Hive. If you write this architecture up for a team, the accurate version is: Kappa removes the second code path for reprocessing by replaying the same streaming pipeline from an earlier offset; it was proposed as an alternative worth considering when simplicity matters, not a categorical replacement of batch.

## Replay is the streaming form of backfill

Replaying a topic from an earlier offset and backfilling a batch pipeline over a date range are the same engineering move, aimed at the same problem — a bug was found, or logic changed, and history needs to be recomputed — expressed in the vocabulary of two different substrates. A backfill re-runs a windowed batch task over the partitions it should have produced; a replay re-runs a stream processor over the offsets it already saw once. Neither one is reaching for new data; both are re-deriving output from data that was already durably captured, which is exactly why both are safe to describe as "backfill" without qualification.

This skill owns the streaming half of that story — replay from an offset, covered above — and stops there deliberately. Partition-level backfill mechanics — how a batch task declares its window, what determinism a rerun requires, how backfills get isolated from production, how late-arriving data changes the picture — belong to [`idempotency-and-backfills.md`](../../pipelines-architecture-data-engineering/references/idempotency-and-backfills.md#backfills) in the orchestration domain, and this file won't re-teach that material. The relationship to hold onto: whichever substrate you're on, "reprocess correctly" reduces to the same question — can you re-derive this output deterministically from data you still have — and the two files together answer it for both substrates instead of one file trying to cover both.

## Choosing an engine

Four names come up in almost every streaming design conversation: Kafka Streams, Flink, Spark Structured Streaming, and Beam. They are not interchangeable, and none of them is the right default — each trades latency, state complexity, ecosystem fit, and operational burden differently, and the team that has to run the thing at 3 a.m. usually decides the trade more than any benchmark does.

**Kafka Streams** is not a cluster you stand up — it's a client library. Kafka's own documentation is direct about this: it's "a simple and lightweight client library, which can be easily embedded in any Java application," with "no external dependencies on systems other than Apache Kafka itself," and it processes "one-record-at-a-time... to achieve millisecond processing latency" (Kafka Streams documentation, "Core Concepts," version 4.3). Scaling means running more instances of your own application, not provisioning a separate execution cluster — the lowest operational floor of the four, but tightly coupled to Kafka as both source and sink. It's the natural choice when the team is already all-in on Kafka and the transformation logic fits inside a JVM service that's already being deployed anyway.

**Flink** is a true streaming engine in the sense that it processes events continuously through the job graph rather than slicing the stream into discrete batches. Flink's own documentation makes this concrete by contrasting its two execution modes: in streaming mode, "all tasks need to be online/running all the time," and "records are immediately sent to downstream tasks... because when processing a continuous stream of data there are no natural points (in time) where data could be materialized between tasks" — which it contrasts directly with its own batch mode, where "the tasks of a job can be separated into stages that can be executed one after another" (Flink documentation, "Execution Mode," stable/v2.3.0). That continuous model is also what its checkpointing rides on: distributed snapshots using barriers that flow through the dataflow, based on the Chandy-Lamport algorithm, plus an embedded RocksDB state backend for state that exceeds available memory — both already established in [`state-and-delivery-guarantees.md`](state-and-delivery-guarantees.md#state-backends-where-the-memory-actually-lives). Flink is the strongest choice when event-time correctness and large keyed state are the hard part of the problem, at the cost of running and operating its own dedicated cluster (JobManager plus TaskManagers) — heavier infrastructure than a library, lighter than a full lakehouse-scale platform.

**Spark Structured Streaming** runs on Spark's micro-batch engine by default: "Structured Streaming queries are processed using a micro-batch processing engine, which processes data streams as a series of small batch jobs... achieving end-to-end latencies as low as 100 milliseconds" (Spark documentation, "Structured Streaming Overview," version 4.2.0). Its biggest advantage isn't a streaming-specific feature at all — it's that it reuses the same DataFrame and SQL API, windowing, and join primitives as Spark's batch engine, the unification [`stream-processing-patterns.md`](stream-processing-patterns.md#how-this-is-expressed-across-engines) already covers. A team with an existing Spark batch estate gets a streaming path without learning a second engine's programming model. Spark also ships a **Continuous Processing** mode promising ~1ms latency, but it's labeled `[Experimental]` in the current (4.2.0) documentation, and the text describing it still reads "As of Spark 2.4, only the following type of queries are supported" — language that hasn't been substantively revised across several major versions. Treat it as experimental and apparently stalled, not as an actively developed low-latency alternative; if sub-second latency is a hard requirement, that requirement argues for Flink, not for reaching for Spark's continuous mode.

**Beam** is not an engine at all — it's the portable model, and the same one that gave this skill's event-time vocabulary its shape: the four questions (what, where, when, how) that [`event-time-windows-and-watermarks.md`](event-time-windows-and-watermarks.md#triggers-and-the-frame-that-ties-all-of-this-together) already builds on come from the Dataflow Model paper Beam implements. Beam's own glossary is explicit about the division of labor: "A runner runs a Beam pipeline using the capabilities of your chosen data processing engine" — the Flink runner "translates a Beam pipeline into a Flink job," and other runners do the equivalent for their own targets (Beam documentation, "Basics of the Beam model," Runner glossary entry). Choosing Beam means choosing portability across engines and buying an extra abstraction layer to get it — worth it if the team genuinely needs to move a pipeline between runners (on-prem Flink today, a managed cloud runner tomorrow) or is already standardized on the Beam SDK for other reasons; overhead with no payoff if the team will only ever run on one engine.

None of these four is a universal answer, and picking a favorite here would contradict the point of laying them out this way. Line them up against the four axes that actually decide:

- **Latency tolerance.** Kafka Streams and Flink both process record-by-record rather than in batches, which is what makes sub-100ms latency reachable at all; Spark's default micro-batch engine floors out around 100ms, and its lower-latency Continuous mode isn't a safe bet given its experimental, apparently-stalled status.
- **State and event-time complexity.** Flink's watermark model, allowed-lateness handling, and RocksDB-backed state for keyed aggregations larger than memory are the most developed of the four for genuinely hard stateful, out-of-order workloads; Kafka Streams' local state stores — fault-tolerant, embedded per task, queryable in place — handle moderate state well without a separate cluster; Spark's watermark-and-output-mode semantics carry the nuance [`event-time-windows-and-watermarks.md`](event-time-windows-and-watermarks.md#spark-structured-streamings-actual-behavior--and-why-late-data-is-dropped-is-not-a-safe-blanket-statement) already documents in detail.
- **Existing ecosystem.** A shop already deep in Kafka gains the least new infrastructure from Kafka Streams; a shop already deep in Spark batch gains the most reuse from Structured Streaming; a shop that needs to stay engine-agnostic, or that targets a managed runner like Dataflow, is the case Beam's portability was built for.
- **What the team can actually operate.** This is the axis that usually decides in practice, and it runs opposite to raw capability: Kafka Streams asks the least of a team that already runs Kafka, because there's no second cluster to learn; Flink and Spark both require standing up, tuning, and being on call for a dedicated distributed execution cluster; Beam adds its own abstraction on top of whichever of those clusters ends up underneath it. The most capable engine on paper is not the right choice for a team that can't staff its 3 a.m. page.

## Operations: the vital signs

Three signals matter more than any dashboard vanity metric once a streaming pipeline is live.

**Consumer lag is the vital sign.** It's the gap, per partition, between the latest offset a producer has written and the offset a consumer group has committed — a direct consequence of the offset mechanics [`the-log-and-partitioning.md`](the-log-and-partitioning.md#consumer-groups-and-rebalance) already established: an offset marks position, and committing it is what makes progress durable and resumable. Lag that's flat or shrinking means the consumer is keeping pace with production; lag that's climbing means processing is falling behind the rate data is arriving, and if it climbs long enough, either it breaches the topic's retention window (data expires before anything ever reads it) or it breaches a downstream SLA first. Alert on the trend, not a single snapshot — a momentary spike during a deploy or a rebalance is normal; a lag that keeps climbing after the rebalance that caused it settles is not, and rebalance frequency itself is a signal in the same category, worth the same attention this file's sibling already gives it.

**Backpressure is what a well-built pipeline does instead of falling over when a downstream stage can't keep up.** A slow sink, an expensive join, or a stateful operator under a sudden spike in unique keys all produce the same shape of problem: work arrives faster than it can be consumed. The failure to avoid is unbounded buffering that eventually exhausts memory, or — worse — silently dropping records to keep up. A properly backpressured pipeline instead signals upstream to slow down, so the queue of unprocessed work stays visible (as lag) rather than invisible (as a buffer growing until it isn't). Rising lag paired with steady or falling throughput is usually backpressure working as intended; rising lag paired with rising memory or GC pressure on a stateful operator is usually backpressure not keeping up with the actual demand, and a signal to add capacity or shed load deliberately rather than let the system decide for you.

**Partitions are the hard ceiling on consumer-group parallelism.** [`the-log-and-partitioning.md`](the-log-and-partitioning.md#topic-partition-offset-the-partition-is-a-double-atom) already established this as the unit of parallelism: one partition is read by exactly one consumer within a group at a time, so a topic with twelve partitions supports at most twelve consumers doing useful work in that group — a thirteenth instance sits idle no matter how much compute it's given. This has two operational consequences worth planning for rather than discovering under load: partition count has to be set with future scale in mind, because increasing it later doesn't rebalance existing keyed data cleanly, and a skewed key distribution can starve this ceiling further by concentrating load on one partition regardless of how many consumers are waiting.

**Schema evolution is not this file's material.** Once a stream's producers and consumers are independently deployed, the schema each side expects has to change safely — that's a data contract problem, and it's governed by a registry enforcing compatibility (backward, forward, or full) rather than by convention. [`data-contracts-and-schema-compatibility.md`](../../quality-data-engineering/references/data-contracts-and-schema-compatibility.md#enforcing-compatibility-confluent-schema-registry) owns that material in full, including the compatibility modes and the specific rules that make "just add a field" less universally safe than it sounds; this file only flags that streaming pipelines need it and points there rather than restating it.

## Closing the loop

Everything in this file — Lambda's cost, Kappa's replay mechanism, four engines and the axes that separate them, the operational signals that keep any of them healthy — is scaffolding for a decision that only matters once one prior question has been answered honestly: does this workload actually need to stream at all. [`unbounded-data-and-when-not-to-stream.md`](unbounded-data-and-when-not-to-stream.md) is where that question gets asked, and it comes first for a reason. An architecture chosen well for a latency requirement that was never real is still the wrong architecture, however correctly Lambda's cost was avoided or however well the engine fit the team's ecosystem. Ask for the number before naming the engine — that discipline doesn't end once streaming is justified; it's just applied one layer down, to which engine, from here on.
