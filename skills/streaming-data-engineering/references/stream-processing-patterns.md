# Joins, Table Enrichment, and CDC as a Stream

The prior files gave this skill its vocabulary: an append-only log with per-partition ordering, event time versus processing time, watermarks as a bet about completeness, and state that has to survive a crash under one of three delivery guarantees. This file is where that vocabulary turns into the patterns a real pipeline actually reaches for — joining one stream against another, enriching a stream against reference data, treating a database's change feed as a stream in its own right, and deduplicating what an at-least-once source hands you. All four turn out to be variations on one idea, which is where the file ends up.

## Stateless vs. stateful, and where validation belongs

[`state-and-delivery-guarantees.md`](state-and-delivery-guarantees.md#stateful-vs-stateless-and-why-state-is-the-hard-part) already draws the line that matters: a stateless operator reads one event, emits zero or more, and forgets it — a filter, a map, a field rename. A stateful operator has to remember something across events, and everything in this file — a join buffer, a deduplication set, a materialized table — lives on the stateful side of that line.

Per-event schema validation belongs on the stateless side, and it's worth naming exactly where it sits before moving on to the stateful patterns: checking that an incoming event matches its expected shape — the right fields, the right types, nothing missing that a required field demands — is a pure function of that one event. It doesn't need to remember anything about event N-1 to judge event N. What that check validates *against* is a contract, not something a stream processor invents at the edge on its own: [`data-contracts-and-schema-compatibility.md`](../../quality-data-engineering/references/data-contracts-and-schema-compatibility.md#enforcing-compatibility-confluent-schema-registry) is where that contract — and the compatibility modes that govern whether a new schema version is even allowed to ship — actually lives. A stream processor's per-event validation step is the enforcement point; the rules it enforces are owned there, not re-derived here.

Everything from here on is stateful, and stateful is where the interesting design decisions are, because state has to be bounded, or the job eventually runs out of memory or disk on a timeline you can calculate from ingest rate — the same argument [`state-and-delivery-guarantees.md`](state-and-delivery-guarantees.md#stateful-vs-stateless-and-why-state-is-the-hard-part) makes about state generally. Joins are the sharpest version of that problem, so that's where to start.

## Stream-stream joins must be time-bounded

Start from what an unbounded join would actually require. Matching an event from stream A against a matching event from stream B — an order against its corresponding payment, a click against its corresponding impression — means holding onto every event from both sides until its match shows up, because you don't know in advance how long that will take. Without a bound on how long you're willing to wait, "how long to hold onto an unmatched event" has no answer, which means the honest implementation is "forever" — retain the complete history of both streams, indefinitely, just to keep the join buffer correct. That's not a design choice degrading gracefully under load; it's infinite state by construction, and it fails the same way any unbounded state does: it runs out of memory or disk on a schedule set by ingest rate, not by anything the join logic controls.

A time bound is what converts that into something finite. If you're only willing to match an order against a payment that arrives within, say, 30 minutes, the engine only has to retain 30 minutes of unmatched events on each side before it can safely give up on a match and release that state — the same watermark-driven state release that closes a window in [`event-time-windows-and-watermarks.md`](event-time-windows-and-watermarks.md#completeness-is-an-estimate-not-a-fact--and-the-watermark-is-that-estimate-made-mechanical), applied to a join buffer instead of an aggregate. The watermark is what tells the engine "no more payments are coming for orders this old" the same way it tells a window "no more events are coming for this bucket" — without it, the join has no principled way to know when to stop waiting.

Spark Structured Streaming's documented support matrix for stream-stream joins makes the bound's role explicit rather than implicit, and it's worth stating precisely because inner and outer joins don't treat the bound the same way:

| Join type | Watermark/time-bound requirement |
|---|---|
| Inner | Optional — you can specify a watermark and time constraint on both sides for state cleanup, but an unbounded inner join is allowed to run without one |
| Left outer | Watermark on the right side and a time constraint are **required** for correct results; a watermark on the left side is optional, for full state cleanup |
| Right outer | Watermark on the left side and a time constraint are **required** for correct results; a watermark on the right side is optional, for full state cleanup |
| Full outer | A watermark on one side and a time constraint are **required** for correct results; a watermark on the other side is optional |
| Left semi | Watermark on the right side and a time constraint are **required** for correct results; a watermark on the left side is optional |

The asymmetry has a real reason behind it, and it's not arbitrary: an outer join has to eventually emit a `NULL`-padded row for a side that never got a match, and the engine can only make that call once it's confident nothing will show up later to match it — exactly the kind of completeness judgment a watermark exists to make. An inner join never has to make that call — a row with no match just never gets emitted, watermark or not — which is why the bound is optional there but load-bearing for every outer variant. Spark's documentation also restricts stream-stream joins to Append output mode as of its current documented state; that restriction is written in terms that trace back to Spark 2.4 and haven't been revised since, so treat it as the current documented behavior rather than something likely to loosen soon.

## Stream-table join: the workhorse

Most enrichment in a real pipeline isn't stream-to-stream at all — it's a stream joined against reference data that changes far less often: an order stream enriched with the customer's tier, a clickstream enriched with a product's current category. This is the pattern that does the most work in practice, precisely because it doesn't carry the stream-stream join's time-bound problem: the reference side isn't another unbounded stream you have to buffer against a watermark, it's a table, looked up by key, that gets refreshed as its own source changes.

[`the-log-and-partitioning.md`](the-log-and-partitioning.md#retention-vs-compaction--and-the-sentence-that-matters) already did the work this section builds on: a compacted topic keeps at least the final record per key, forever, which makes **a compacted topic a table** — current state per key, materialized from a stream of changes. Kafka Streams gives that idea a name and a lookup interface, and it's worth stating the relationship precisely rather than as an equation: a KTable is "an abstraction of a changelog stream, where each data record represents an update" — each value read as an UPSERT of the last value for the same key, and a null value read as a delete — and it "provides an ability to look up current values of data records by keys," available "through join operations... as well as through Interactive Queries" (Kafka Streams documentation, "Streams DSL," version 4.3). Compaction is the storage counterpart of that idea, not its definition: Kafka's own docs frame it as what you'd "probably want to enable" on a topic holding a KTable, and warn that enabling it under a KStream would break that stream's semantics. So the accurate reading is that a KTable is a changelog stream materialized into a keyed, queryable current-state view, and compaction is what makes a topic a safe durable home for one — not that the two are the same object. A stream-table join — a KStream against a KTable, or the equivalent construct in another engine — is a dimensional lookup performed in real time: for each event on the stream side, look up the current row for its key on the table side, and attach it.

The interesting case is what "current" means when the reference data isn't just an overwritten row but a Slowly Changing Dimension Type 2 table — one that keeps history instead of destroying it. [`scd-and-dimension-patterns.md`](../../modeling-data-engineering/references/scd-and-dimension-patterns.md#late-arriving-dimensions-and-facts) already makes the batch-side version of this argument: a late-arriving fact has to join against the dimension row whose effective/expiration window contains the fact's own business date, never the row flagged as current today. A streaming stream-table join against an SCD Type 2 dimension is that exact same argument, live: enrichment has to be as-of the event's own timestamp, not as-of whenever the join happens to execute. An order event from three days ago that gets reprocessed today should pick up the customer tier that was in effect three days ago, not today's tier — the same effective-dated lookup the modeling file already established, now running continuously against a stream instead of once against a backfill window.

## CDC as a stream

This is the section two other skills in this suite have been pointing at without an answer, so it earns a direct one. Change Data Capture, done the way tools like Debezium do it, is a stream in the same sense everything above is a stream — not a metaphor borrowed for convenience.

**It reads the transaction log, not the table.** Rather than polling a table on a schedule and diffing what changed — the pattern [`engineering-query-patterns.md`](../../sql-data-engineering/references/engineering-query-patterns.md#incremental-extraction-the-watermark-pattern) covers under incremental extraction — log-based CDC reads the database's own write-ahead log (PostgreSQL's WAL) or binary log (MySQL's binlog), the same durability mechanism the database already maintains for its own crash recovery. That's a fundamentally different mechanism from polling: it doesn't touch the source tables at read time at all, and it produces a change event within moments of the commit rather than however long the polling interval happens to be.

**One committed change produces one event, and that event carries the operation type.** Every change event carries an `op` field naming exactly what happened — `c` for create, `u` for update, `d` for delete — and two values worth knowing that a simplified create/update/delete summary usually drops: `r` for a row produced during the initial snapshot rather than live streaming, and `t`/`m` for truncate and generic message events. The `r` value is the piece that connects this claim to the next one — it's how the connector marks a snapshot-sourced row as structurally the same kind of event as a live change, sharing one event format across both.

**Snapshot, then stream, is the standard flow.** A transaction log doesn't retain forever — PostgreSQL purges WAL segments, MySQL rotates binlogs — so a connector that started capturing today has no way to reconstruct a table's full history from the log alone. The standard flow closes that gap: take a consistent snapshot of the table's current state first, then start streaming changes from the exact log position the snapshot was taken at, so nothing that happened during the snapshot itself gets missed. That's why the `r` operation type exists — it's how the snapshot's rows travel through the same event stream the live changes use.

**Delivery is at-least-once, which means the consumer has to deduplicate — but the honest version of that claim has a condition attached.** Under normal operation, a consuming application sees each event exactly once. The at-least-once exposure shows up specifically around failure and recovery: if the CDC connector crashes before it records its last processed position, or a network failure means it never receives confirmation that an event was delivered, it resumes from the last position it knows about and can redeliver an event the consumer already saw. The practical consequence doesn't change: a consumer can't know in advance whether today is a day nothing fails, so the deduplication logic has to exist regardless, even though duplicates aren't the constant background noise a flat "always at-least-once" framing would suggest.

This closes the pointer both `modeling` and `quality` have been carrying: CDC capture is a log-read mechanism producing a typed, ordered event per committed change, snapshot-seeded, at-least-once under failure. What those two skills correctly kept out of scope — how the resulting change stream gets projected back into a queryable current-state table — is exactly the `MERGE` pattern [`engineering-query-patterns.md`](../../sql-data-engineering/references/engineering-query-patterns.md#idempotent-upserts-with-merge) already owns: apply each change event's `c`/`u`/`d` by key, and the target table converges to current state regardless of how many times a given event gets redelivered. That SQL doesn't need restating here — the piece this file adds is what the stream feeding that `MERGE` actually is and why it behaves the way it does.

## Deduplication bounded by a watermark

The at-least-once guarantee just established isn't an abstract risk — it's the concrete reason a streaming pipeline needs a deduplication step at all, and [`state-and-delivery-guarantees.md`](state-and-delivery-guarantees.md#the-three-delivery-semantics) is where that guarantee is defined in the first place: "nothing is ever silently lost, but retries after a failure can redeliver something already processed, producing duplicates unless something downstream removes them." Deduplication is that removal.

The mechanism is a keyed set of identifiers already seen — a natural key on a CDC event, an idempotency key on an API call, a message ID on a queue delivery — checked before processing and inserted after. The set can't be unbounded any more than a join buffer can: if it held every ID ever seen, it would grow for as long as the pipeline runs, which is exactly the unbounded-state problem stream-stream joins ran into above. A watermark bounds it the same way it bounds a join buffer: once event time has advanced far enough past a given ID's arrival that a duplicate delivery of it is no longer plausible, the ID can be evicted from the dedup set. That's the same trade [`event-time-windows-and-watermarks.md`](event-time-windows-and-watermarks.md#the-watermark-trade-there-is-no-universally-correct-setting) already names for any watermark setting — a longer window catches more duplicates that arrive with more delay, at the cost of a larger retained set; a shorter window bounds memory tighter, at the cost of missing a duplicate that shows up later than expected. There's no dedup-window setting that's correct in the abstract, only one that's correct against a stated tolerance for how late a redelivered event might arrive.

## How this is expressed across engines

Every pattern above shows up as a first-class construct across the major stream-processing tools, not as something you build from scratch each time. Kafka Streams gives the stream-table distinction its own types — a record stream and a changelog stream materialized as a table — with join operators between them built in. The streaming SQL layers built on top of stream-processing engines let you express the same joins, enrichments, and windowed aggregations as SQL statements running continuously over streams and tables rather than as one-time queries over static data. Spark Structured Streaming extends its DataFrame and SQL API with the same windowing and join primitives covered above, layered onto the engine whose micro-batch execution model and watermark semantics were already established in the earlier files of this skill.

The observation worth carrying out of this section is the unification [`unbounded-data-and-when-not-to-stream.md`](unbounded-data-and-when-not-to-stream.md#what-the-model-says-about-batch-and-streaming--not-the-popular-paraphrase) already sets up: a windowed aggregation written against a live topic and the same aggregation written against a warehouse table read the same way, because the underlying model was built so boundedness changes how often a result gets emitted, not what the operation means. `GROUP BY` a tumbling window over a stream and `GROUP BY` a date column over a batch table are the same grouping logic wearing two different clocks — one continuously evaluated against event time as it arrives, one evaluated once against a column that's already fully landed. Recognizing that isn't a curiosity; it's what makes a SQL-fluent engineer productive in a streaming SQL engine on day one instead of having to relearn aggregation from scratch.

## The unifying idea

Pull every pattern in this file back together and one sentence covers all of them: **a streaming table is a materialized view that keeps itself current.** A KTable is a changelog stream read as upserts and exposed through a key lookup. A stream-table join is a real-time lookup against exactly that kind of continuously current table. A CDC change stream, projected through the `MERGE` pattern this file deferred to SQL, produces exactly that kind of table as its output. And the compacted topic underneath all of it is the same mechanism [`the-log-and-partitioning.md`](the-log-and-partitioning.md#retention-vs-compaction--and-the-sentence-that-matters) already named as the stream-table duality made literal.

None of these are four separate techniques that happen to resemble each other. They're one relationship — the stream is the change record, the table is its current state — looked at from four different points in a pipeline: where the reference data lives (the KTable), where the enrichment happens (the stream-table join), where the change originates (CDC), and what materializes the two into and out of each other (compaction and `MERGE`, each doing the same conversion in its own layer). Once that relationship is visible, "should this be a stream or a table" stops being a question with a real answer — every table here is a stream that's been asked to hold still for a moment, and every stream is a table's history, replayed.

## Common mistakes

| Mistake | Why it hurts | Fix |
|---|---|---|
| Joining two streams with no watermark or time bound on either side | The join buffer has to retain every unmatched event from both sides indefinitely — infinite state on an unbounded input | Bound the join with a watermark and time constraint on at least the side the join type requires, and size the bound against how late a real match can plausibly arrive |
| Assuming an outer stream-stream join needs the same bound as an inner one | Spark's support matrix requires a watermark for correct outer-join results specifically, because emitting the unmatched `NULL` row needs a completeness judgment an inner join never has to make | Treat outer joins as requiring the bound, inner joins as optional but still advisable for state cleanup |
| Enriching a stream against an SCD Type 2 dimension by looking up "current" instead of as-of the event's own timestamp | A reprocessed or delayed event picks up today's dimension state instead of the state that was actually in effect when it happened, silently corrupting historical enrichment | Look up the dimension row whose effective/expiration window contains the event's own timestamp, the same as the batch late-arriving-fact case |
| Describing Debezium-style CDC as "always at-least-once, so duplicates are constant" | Normal operation delivers exactly once; at-least-once exposure is specific to connector crash and network-failure recovery | State the condition: the consumer must be able to deduplicate because it can't know in advance which runs will hit a failure, not because duplicates are the steady-state norm |
| Letting a deduplication key set grow without a bound | An unbounded set of "seen" IDs grows for as long as the pipeline runs, the same failure shape as an unbounded join buffer | Bound the dedup set with a watermark-driven eviction window sized to a stated tolerance for how late a redelivered event might arrive |
| Treating a windowed streaming aggregation as a fundamentally different operation from a batch `GROUP BY` | It's the same grouping logic evaluated against a different clock — event time arriving continuously versus a column already fully landed | Carry SQL aggregation fluency directly into a streaming SQL engine instead of relearning the operation from scratch |
