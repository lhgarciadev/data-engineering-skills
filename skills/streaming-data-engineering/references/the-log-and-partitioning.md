# The Log, Partitioning, and Durability

Everything a stream processor does — windowing, joining, aggregating, recovering from a crash — is built on top of one structure: an append-only log. Get the log's guarantees right in your head and the rest of this skill is mostly mechanics on top of a substrate you already understand. Get them wrong — usually by assuming the log promises more order or more durability than it does — and you inherit a class of bug that only shows up under load, at scale, or after a failover, which is exactly when it's most expensive to discover.

This file uses Apache Kafka's log model as the concrete referent, because it's the log implementation this skill's later files build on directly. The guarantees described here are Kafka's, verified against its current (4.3) documentation; where the wording matters as much as the concept, this file says so.

## The log as the central abstraction

A Kafka topic is, at its core, an append-only sequence of records. Nothing is ever edited in place, and nothing is removed except by an explicit retention or compaction policy (covered below). A producer appends; a consumer reads forward from wherever it left off. That's the entire write model — no `UPDATE`, no `DELETE`, no in-place mutation of a record once it's written.

This is the same abstraction the event-log framing in [`modeling-for-access-patterns.md`](../../modeling-data-engineering/references/modeling-for-access-patterns.md) describes from the modeling side: an immutable, ordered record of facts, where any "current state" a consumer cares about — the latest price, the latest account balance, the latest shipping address — is not stored directly but *derived* by folding the log forward from some starting point. That file calls this the stream-table duality: a stream is a table's changelog, and a table is a point-in-time snapshot of a stream. Here, that duality stops being a modeling abstraction and becomes an engineering fact about how Kafka is built: the log is the source of truth, and every materialized view over it — a consumer's in-memory state, a compacted topic, a downstream table — is a projection that can, in principle, be rebuilt from the log alone. Keep that sentence in mind; the compaction section below makes it concrete.

## Topic, partition, offset: the partition is a double atom

A topic is a named log. But a topic is never really one log — it's split into **partitions**, and the partition, not the topic, is where Kafka's actual guarantees live.

A partition is the atom of two different things at once, and conflating them is where a lot of streaming design goes wrong:

- **The unit of parallelism.** Each partition can be consumed independently, which is what lets a consumer group split the work of one topic across multiple processes or threads — one partition, one consumer within the group, at any given time.
- **The unit of ordering.** Kafka's current documentation states the ordering guarantee positively and precisely: "Kafka guarantees that any consumer of a given topic-partition will always read that partition's events in exactly the same order as they were written." Order is a property of a single partition's write sequence, full stop.

Nothing in that guarantee extends across partitions. Two records written to different partitions of the same topic carry no promise about their relative order at all — not "usually ordered," not "ordered under normal conditions," just no guarantee. (Kafka's own documentation stated this negative half explicitly in its 0.8.2-era introduction — "Kafka only provides a total order over messages within a partition, not between different partitions in a topic" — and while the current docs no longer spell out the negation in those words, the partitioning model that produces it hasn't changed since. The positive guarantee quoted above is the current wording; the absence of a cross-partition promise is the direct, unavoidable consequence of it, not a separate fact you have to go looking for elsewhere.)

This is worth stating as plainly as the brief for this file demands, because it's the single most common source of subtle correctness bugs in streaming systems: **a whole class of bugs is nothing more than assuming a total order across a topic that Kafka never promised.** A dashboard that reads two partitions and expects event A (written first, to partition 0) to always precede event B (written slightly later, to partition 1) will occasionally be wrong, and it will be wrong in a way that's nearly impossible to reproduce on demand, because the actual interleaving depends on producer batching, broker load, and consumer fetch timing — none of which are under your control and none of which Kafka owes you an ordering promise about. If your logic needs A before B, either put both on the same partition (see the next section) or design the consumer to tolerate arbitrary interleaving across partitions, but do not write code that silently assumes one.

## Partition key: the design decision that decides both ordering and load

How a record lands on a partition isn't random by default — it's a decision you make, once, when you choose (or don't choose) a partition key.

The default partitioner hashes the record's key and uses that hash to pick a partition. Two records with the same key hash to the same partition every time, which is the *only* mechanism Kafka gives you for guaranteeing relative order between two records: put them on the same partition by giving them the same key. That's why per-entity ordering — "all events for this customer arrive in the order they happened," "all updates to this account are ordered" — is achieved by keying on the customer ID or account ID, not by any topic-level setting. There is no topic-level "preserve order" switch; order is a consequence of key choice, nothing else.

That mechanism cuts both ways. The same hash-by-key routing that gives you per-entity order is also what produces **skew** the moment your key distribution is uneven. A key that accounts for a disproportionate share of traffic — one large tenant in a multi-tenant system, one high-volume device ID, one status value in an otherwise low-cardinality key — sends a disproportionate share of records to one partition. That partition's consumer falls behind while the others sit idle, and because consumer count is capped by partition count, you cannot fix it by adding more consumers; the hot partition is still one partition, however many consumers are waiting for work.

This is the identical failure shape covered in [`joins-and-skew.md`](../../spark-data-engineering/references/joins-and-skew.md) for Spark shuffles — one task or one partition carrying far more data than its peers while the rest finish and wait — just relocated to ingest time instead of query time. The important difference is that Spark's skew has a runtime repair: Adaptive Query Execution detects a skewed shuffle partition after the fact and splits it. Kafka's partitioning has no equivalent. There is no adaptive re-partitioning of a live topic; the key you chose at write time is the load distribution you're stuck with until you change the key or repartition the topic, both of which are migrations, not runtime knobs. That asymmetry is the actual argument for treating partition-key choice as a design decision made with real criteria, not a mechanical afterthought:

- **Prefer a key with high, even cardinality relative to your partition count.** An ID space (customer ID, device ID, order ID) that's large and roughly uniformly distributed spreads load evenly across partitions almost for free.
- **Key on the entity whose *order* you actually need, not the entity that's convenient.** If you need per-account ordering, key on the account ID even if some other field is easier to extract — ordering correctness should drive the key, not code simplicity.
- **Audit for a dominant key before you ship, not after.** If one tenant, one device, or one status is going to carry 30% of your volume, know that going in. A hot key that was tolerable at today's volume can become the partition that falls permanently behind at tomorrow's.
- **When per-entity ordering isn't required at all, key on nothing (`null`).** The default partitioner's behavior for an unkeyed record is **sticky**, not round-robin: it sends records to one partition until at least `batch.size` bytes have gone to it, then switches to a different "sticky" partition. (A true round-robin partitioner exists as a separate, non-default class, and Kafka's own configuration reference flags a known issue — KAFKA-9965 — that causes uneven distribution with it on new batches; it isn't the safer default it sounds like.) Don't invent an artificial key just to have one, either — an unnecessary key is a self-inflicted skew risk with no ordering benefit to show for it.

Choosing a partition key is choosing, simultaneously, what gets ordered together and how load is spread. There is no way to optimize one axis without constraining the other — that trade is the whole decision.

## Consumer groups and rebalance

A consumer group is Kafka's mechanism for spreading a topic's partitions across multiple consumer processes while guaranteeing each partition is read by exactly one consumer in the group at a time — that's what lets a group of N processes divide a topic of M partitions between them instead of each process re-reading everything. Kafka's own client documentation states the trigger conditions plainly: "if a process fails, the partitions assigned to it will be reassigned to other consumers in the same group. Similarly, if a new consumer joins the group, partitions will be moved from existing consumers to the new one." The same reassignment fires when partitions are added to a subscribed topic. This reassignment event is called a rebalance.

A rebalance is worth treating as an operational fact, not background noise, and the reason follows directly from a mechanic already established above: the committed offset lives at the level of the consumer *group and partition*, not the process instance holding the partition at a given moment — which is exactly why the new owner can pick up where the old one left off at all. That same fact is what makes the handoff lossy in one direction: while partitions are being reassigned, the consumers involved aren't making progress on those partitions, and any records processed after a consumer's last committed offset but before it loses the partition get reprocessed by whichever consumer picks it up next, because the new owner has no way to know about progress the old owner made but never committed — it resumes from the last *committed* offset, not from wherever the previous owner actually got to. A group that rebalances constantly — because instances are crash-looping, because a deploy restarts every consumer at once, because a health check is too aggressive and evicts a slow-but-alive consumer — pays for that churn twice: in the direct pause during each reassignment, and in duplicate processing of whatever wasn't committed yet. A rebalance rate that's climbing is a signal worth alerting on, in the same category as rising consumer lag, not a detail to notice only after something downstream breaks.

## Durability: `acks` and the in-sync replica set

Whether a record you produced is actually safe once the producer call returns is not a property of the cluster's configuration alone — it's a decision the producer makes, per write, through the `acks` setting. That's why it belongs here, in a discussion of the log's guarantees, rather than in an infrastructure conversation about broker or cluster setup: `acks` is set in producer configuration, and it trades latency for durability at the point where each individual write happens, not once for the whole deployment.

Kafka's producer configuration documents three settings:

- **`acks=0`** — fire-and-forget. The producer doesn't wait for any acknowledgment; the record is considered sent the moment it hits the socket buffer. "No guarantee can be made that the server has received the record."
- **`acks=1`** — the partition leader acknowledges after writing to its own local log, without waiting for followers to replicate. Fastest of the three that offers any guarantee at all, but "should the leader fail immediately after acknowledging the record but before the followers have replicated it then the record will be lost."
- **`acks=all`** (equivalent to `acks=-1`) — the leader waits for the full set of **in-sync replicas** to acknowledge before responding. "This guarantees that the record will not be lost as long as at least one in-sync replica remains alive. This is the strongest available guarantee."

The precision that matters, and that's easy to lose in casual explanation: `acks=all` does not mean every replica *assigned* to the partition acknowledged the write. It means every replica currently in the **in-sync replica (ISR) set** acknowledged it — and the ISR set can be smaller than the full replica set. Kafka's own design documentation is explicit about the consequence: "if a topic is configured with only two replicas and one fails (i.e., only one in sync replica remains), then writes that specify `acks=all` will succeed. However, these writes could be lost if the remaining replica also fails." The system chose to keep the partition available rather than block writes when the ISR shrinks, and that choice is itself configurable — `min.insync.replicas` lets you require a larger minimum ISR before a write with `acks=all` is accepted, trading some availability back for a durability floor that doesn't silently erode as replicas fail.

The trade in one line: `acks=0` is fastest and offers nothing, `acks=1` risks losing exactly the record that was in flight during a leader failure, and `acks=all` is the strongest guarantee Kafka gives — but "strongest available" is bounded by whatever the ISR happens to be at the moment of the write, not by the topic's replication factor on paper.

## Retention vs. compaction — and the sentence that matters

Kafka gives you two independent ways to decide how long a record stays in the log, and they answer different questions. **Retention** (by time, `retention.ms`, or by size, `retention.bytes`) answers "how far back can a consumer read." **Compaction** answers a different question entirely: "for this key, what's the latest value," and it does so by discarding older records for a key once a newer one exists, rather than discarding by age.

The precise guarantee is easy to overstate, and the common shorthand — "compaction keeps only the last message per key" — overstates it in three specific ways that Kafka's own design documentation is explicit about:

1. **The guarantee is "at least," not "exactly one."** Kafka's documented guarantee is that "any consumer progressing from the start of the log will see **at least the final state** of all records in the order they were written." Compaction happens on the *tail* of the log, on a delay governed by `min.compaction.lag.ms` / `max.compaction.lag.ms`; until a key's older records are actually compacted away, more than one record for that key can coexist in the log.
2. **The active segment is never compacted, regardless of age.** "The active segment will not be compacted even if all of its messages are older than the minimum compaction time lag." The segment currently being written to is always exempt — compaction only ever operates on already-closed segments.
3. **Deletes (tombstones) are not permanent.** A record with a `null` value for a key is a tombstone — it marks that key as deleted and causes prior records for that key to be removed. But the tombstone itself is cleaned up after `delete.retention.ms` (24 hours by default), and a consumer lagging behind by more than that window can miss the tombstone entirely and never learn the key was deleted.

None of that weakens the practical conclusion — it sharpens it. Because compaction guarantees at least the final state per key survives indefinitely (subject to the active-segment and tombstone-timing caveats above), **a compacted topic is a table**: current state per key, materialized from a stream of changes, retrievable by reading the topic from the start. That's the stream-table duality made literal and operational, not just a modeling analogy — the same relationship [`modeling-for-access-patterns.md`](../../modeling-data-engineering/references/modeling-for-access-patterns.md) describes ("a table can be considered a snapshot, at a point in time, of the latest value for each key in a stream") is what a compacted topic *is*, implemented as a retention policy rather than derived after the fact by a downstream job. Anywhere this skill later builds a materialized, queryable view of "current state" directly out of a stream of change events, this is the mechanism underneath it.

## Replayability: the property that makes recovery, reprocessing, and Kappa possible

Everything above compounds into one property that the rest of this skill leans on repeatedly: a Kafka log is **replayable**. Records aren't consumed-and-discarded the way a traditional queue's messages are; consuming a record doesn't remove it, and a consumer's position in a partition is just an offset it tracks and commits, not a state the broker mutates on read. Kafka's own design documentation states the consequence directly: "A consumer can deliberately rewind back to an old offset and re-consume data. This violates the common contract of a queue, but turns out to be an essential feature for many consumers."

That single capability — rewind and re-read, deliberately, at any time within the retention window — is what makes several things possible that would otherwise each need their own separate mechanism:

- **Recovery.** A consumer that crashes before committing resumes from its last committed offset, reprocessing only what it hadn't yet finished — no special recovery path, just the same read-forward-from-an-offset mechanism used every other time.
- **Reprocessing.** A bug in a stream processor's logic, discovered after a week of bad output, doesn't require replaying data from some separate cold-storage backup — if the topic's retention window still covers the affected period, rewinding the consumer's offset and reprocessing is the fix, using the exact same log the original run consumed.
- **The architectural argument for treating the log as a system of record**, rather than a transient pipe, rests entirely on this property: if the log can always be replayed to reconstruct any downstream state, downstream state stops needing to be treated as precious, and can instead be treated as disposable and rebuildable. That argument is what later work in this skill on stream-processing engine design draws on directly — it doesn't need to be re-derived there, because the replayability it depends on is exactly what this section established.

Replayability is bounded by retention, though — it isn't unlimited. A topic retained for seven days can be replayed for anything that happened within the last seven days, not for anything that happened, ever. Compaction changes what's available to replay (current state per key, not full history) rather than removing the time bound; plan retention windows around how far back reprocessing genuinely needs to reach, not around "as long as possible by default."

## Common mistakes

| Mistake | Why it hurts | Fix |
|---|---|---|
| Assuming order holds across a topic, not just within a partition | Kafka's ordering guarantee is scoped to a single partition; two different partitions carry no relative ordering promise at all | Key records that must stay ordered relative to each other onto the same partition, or design consumers to tolerate arbitrary cross-partition interleaving |
| Treating "compaction keeps only the last message per key" as literal | The documented guarantee is "at least the final state," with a non-compacted active segment and tombstones that expire after `delete.retention.ms` | Read a compacted topic as "current state, eventually, with a bounded consumer-lag caveat on deletes" — not as an instantaneous single-row-per-key store |
| Reading `acks=all` as "every replica acknowledged" | It means every replica in the *current* in-sync set acknowledged, which can be smaller than the full replica set if followers have failed | Pair `acks=all` with `min.insync.replicas` if the durability floor must not erode as the ISR shrinks |
| Choosing a partition key without checking its cardinality or hot-key risk | A skewed key sends disproportionate volume to one partition, and Kafka has no runtime repair for that the way Spark's AQE repairs a skewed shuffle | Audit key cardinality and distribution before shipping; prefer high-cardinality, evenly distributed keys, and key on `null` when no ordering guarantee is actually needed |
| Ignoring rebalance frequency as a metric | Frequent rebalances pause affected partitions repeatedly and reprocess whatever wasn't committed before each reassignment | Alert on rebalance rate the same way you'd alert on consumer lag, and investigate crash-looping consumers or overly aggressive health checks before they show up as duplicate processing downstream |
