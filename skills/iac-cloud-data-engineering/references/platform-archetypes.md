# Platform Archetypes

[`choosing-a-managed-service.md`](choosing-a-managed-service.md) names six axes; [`sizing-and-the-cost-model.md`](sizing-and-the-cost-model.md) names three workload shapes. This file spends them. Five stacks recur in every data platform, and each one is a place where an infrastructure decision and a domain decision routinely get mistaken for one another — which is how a team ends up choosing a streaming service to fix an ordering bug, or a bigger cluster to fix a skewed join.

Every archetype below has the same three parts, and the repetition is the point:

- **What the domain skill decides.** Named and linked, never re-taught. If you are reading this file for partition keys, shuffle, grain or DAG design, you are in the wrong file and the right one is one link away.
- **What is decided here.** The six axes — `operational burden`, `scaling granularity`, `coupling`, `throughput shape`, `failure and recovery model`, `ecosystem fit` — applied by name, against the three workload shapes: `steady`, `spiky`, `exploratory`.
- **The one-way door.** Which rung of the reversibility ladder in [`statefulness-and-the-one-way-door.md`](statefulness-and-the-one-way-door.md) this archetype actually sits on, and therefore how much of the design budget it deserves.

Read the third part first. The ladder, not the diagram, decides the order.

## 1. Streaming platform

**What `streaming-data-engineering` decides.** The partition key and what it costs you when it is skewed, the scope of ordering, offsets and consumer groups, `acks` and the in-sync replica set, retention versus compaction, and what replay does to downstream state — all of it in [`the-log-and-partitioning.md`](../../streaming-data-engineering/references/the-log-and-partitioning.md) and its siblings. None of that changes because you bought the log from a vendor instead of running it, and no service selection repairs a wrong key.

**What is decided here.** The service, its capacity mode, and the protocol question.

`Scaling granularity` is the axis that most often gets quoted wrong, because the unit belongs to the mode rather than to the product: MSK Provisioned asks for broker nodes and a broker type while MSK Serverless exposes no broker unit; Kinesis Data Streams exposes the shard in provisioned mode only; Azure Event Hubs uses a throughput unit, a processing unit or a capacity unit depending on tier, and its partitions organise rather than buy capacity; Google Cloud Pub/Sub states that it does not have partitions at all. Name the unit and the mode together or you have named nothing.

`Throughput shape` for an ingest tier is usually `steady` — always-on ingest sits near its peak for most of the operating window — which pushes toward a provisioned shape with a knob on it. Reprocessing and replay are `spiky` against the same infrastructure, and that mismatch is real: the tier is sized for the steady case and then asked to absorb a burst it was not sized for. `Exploratory` does not arise here, because no analyst issues queries against a log; when someone wants to explore the events, the answer is a copy in archetype 3, not a bigger ingest tier.

`Operational burden` runs from entirely yours on self-managed Apache Kafka to a control plane someone else runs, and the honest reading from [`choosing-a-managed-service.md`](choosing-a-managed-service.md) applies unchanged: managed moves the work onto your bill and a ticket queue rather than deleting it. `Failure and recovery model` is where the vendor's own wording matters most, because two services can have the same ordering *scope* and different write guarantees. `Ecosystem fit` includes the question people skip — whether your identity plane reaches the service at all, since a service it cannot reach will be reached by a stored key instead ([`identity-network-and-encryption.md`](identity-network-and-encryption.md)).

**The one-way door.** `Coupling`, and it is worse here than anywhere else in the skill relative to how cheap the infrastructure looks. A proprietary API — Kinesis Data Streams' `PutRecord`/`GetRecords` surface, Pub/Sub's gRPC and REST API — means **the thing you would rewrite is the client code, not the infrastructure**. Producers and consumers live in repositories owned by other teams, on release schedules you do not set, and the migration you priced as an infrastructure project is a coordinated change across all of them. That is the difference between MSK, which AWS says "runs open-source versions of Apache Kafka"; Event Hubs, which Microsoft describes as providing a Kafka *endpoint* that "implements the same protocol"; and an API only one vendor sells. Google makes the argument itself when steering toward its other product: "Apache Kafka APIs are much more broadly adopted."

Add the rung the frame file names separately: **topic names are stateful identity**. Renaming or re-homing a topic is a migration for every consumer whether or not a byte moves. The service sits mid-ladder, the client-code coupling is near-irreversible, and the second one is the one nobody prices.

## 2. Distributed compute (Spark and friends)

**What `spark-data-engineering` decides.** Shuffle and partitioning, join strategy and skew, executor and driver memory, Adaptive Query Execution, caching, file formats, UDF overhead — [`spark-data-engineering`](../../spark-data-engineering/SKILL.md) owns all of it, and [`joins-and-skew.md`](../../spark-data-engineering/references/joins-and-skew.md) and [`memory-management.md`](../../spark-data-engineering/references/memory-management.md) are where a slow or dying job actually gets fixed. A job wrong on those is not repaired by any procurement decision, and buying a bigger cluster hides the defect behind an invoice.

**What is decided here.** Cluster shape, node type, autoscaling policy, and serverless-versus-provisioned.

`Scaling granularity` again refuses to have one name: workers in EMR Serverless, DPUs and M-DPUs behind AWS Glue's worker types, DBUs as Databricks' consumption unit, capacity units and Spark vCores in Microsoft Fabric, and on Google Cloud the current product name is Managed Service for Apache Spark with deployments the vendor calls "on clusters" and "serverless" — the `dataproc` prefix survives in image versions and resource names, so old material reads as current when it is not.

`Throughput shape` decides the provisioning shape rather than the product: `steady` scheduled batch fits capacity held per unit of time, `spiky` event-driven reprocessing fits a consumption shape, and `exploratory` here means an interactive cluster attached to a notebook — where the failure is not a scan meter but a cluster nobody suspended, and the lever is the idle timeout with the non-monotonic caveat [`sizing-and-the-cost-model.md`](sizing-and-the-cost-model.md) attaches to it.

`Operational burden` is where a warm-capacity feature earns or loses its keep; `failure and recovery model` on this archetype includes a question worth asking out loud — when the job fails overnight, can whoever is paged read the logs and change the configuration, or is their action to file a ticket? `Ecosystem fit` is the catalog, the notebook surface and the connectors your team already writes against.

Two things belong here rather than in a tuning ticket. First, autoscaling means **the live worker count is an output, not a declaration** — declare the bounds and the policy object, or your drift report will propose pulling capacity out from under a running job, as [`iac-for-stateful-resources.md`](iac-for-stateful-resources.md) sets out. Second, **Azure Synapse Analytics is not deprecated**: as of 2026-08-08 Microsoft publishes no retirement date for the service and describes it in the present tense; what is published is that Fabric is the recommended start for *new* work, and Fabric's own documentation still directs GPU-accelerated pools, external Hive Metastore and JDBC connections to Synapse Spark. Individual Synapse components have been retired with explicit dates; the service has not.

**The one-way door: mostly none, and that is the useful thing to say.** Compute is the most reversible rung of the ladder. It holds nothing between runs, so reversing means pointing a different engine at the same data and re-running — real work, bounded work. This archetype attracts a disproportionate share of design meetings because it is the biggest box on the diagram, and **that budget belongs to archetype 3.** Decide compute quickly, in the knowledge that you can decide it again.

The narrow exception is not compute at all: where the platform's runtime, catalog and notebook surface become what your team writes against, `coupling` reaches the near-irreversible rungs. Open-source Spark against files in an open table format keeps the job portable even when the platform is not.

## 3. Warehouse / lakehouse

**What the domain skills decide.** Grain, dimensional design, Slowly Changing Dimensions and the medallion layering are [`modeling-data-engineering`](../../modeling-data-engineering/SKILL.md), with [`modern-lakehouse-modeling.md`](../../modeling-data-engineering/references/modern-lakehouse-modeling.md) covering what sits above the format. The queries and their execution — pruning, pushdown, the cost driver per engine — are [`query-optimization-and-production.md`](../../sql-data-engineering/references/query-optimization-and-production.md). The schema those consumers coupled to is governed by [`data-contracts-and-schema-compatibility.md`](../../quality-data-engineering/references/data-contracts-and-schema-compatibility.md).

**What is decided here.** The platform, its billing shape, and the storage/compute separation.

The billing shape *is* the decision, and the product name never gives it to you. Capacity held per unit of time: BigQuery's "Capacity pricing (per slot-hour)", Redshift Serverless "billed according to the capacity used in a given duration, in RPU hours on a per-second basis", Snowflake credits against warehouse uptime. Per-query bytes scanned: Athena's `per-query billing, based on data scanned`, BigQuery's on-demand model. Beneath both sits object storage on its own separate meters — Amazon S3, Azure Blob Storage and Google Cloud Storage each meter storage, requests and transfer separately, among others, though not with the same grouping; [`statefulness-and-the-one-way-door.md`](statefulness-and-the-one-way-door.md) has what each vendor actually names. Azure prints its data-storage unit as `Per GB / per month`, a standing rate against a quantity that only grows.

Cross that against `throughput shape` and one cell explodes: `exploratory` work on a bytes-scanned meter has no ceiling and an invisible driver. `Steady` ELT is the natural fit for capacity held over time; `spiky` loads fit the scan meter well. Give exploratory access a shape with a ceiling and leave the scan meter to workloads whose volume you can predict.

`Scaling granularity` is separation of storage from compute: the ability to resize the query tier without touching the corpus is what keeps the compute decision cheap to reverse while the storage one stays expensive. `Operational burden`, `failure and recovery model` and `ecosystem fit` behave as elsewhere, with one addition — the identity model and the catalog are what every other tool binds to.

Two infrastructure-code specifics land here, because this is the archetype where a plan can destroy history.

**The bucket that refuses to be deleted, and the property that makes it comply.** AWS documents that "AWS CloudFormation does not remove Amazon S3 buckets that contain files even if their removal policy is set to `DESTROY`. Attempting to do so is an AWS CloudFormation error", and that "To have the AWS CDK delete all files from the bucket before destroying it, set the bucket's `autoDeleteObjects` property to `true`." Read both halves. The refusal is a genuine guard — and it is narrow, covering one resource type in one tool, with an opt-out one property away that reads in review like a convenience flag rather than what it is. On the lakehouse's own storage, that flag is a near-irreversible decision written in the vocabulary of a trivially reversible one.

**And the preview you are trusting has an accuracy mode.** `cdk diff` in its default `auto` mode "Creates an AWS CloudFormation change set to display accurate replacement information", but "If the change set can't be created (for example, due to missing permissions), falls back to a template-only diff" — silently, from the reader's point of view. The `template` mode is documented as "Faster, but less accurate. Any change detected to properties that require resource replacement is displayed as a resource replacement, even if the change is purely cosmetic." Both directions hurt on a stateful resource: over-reporting trains reviewers to skim replacement lines, and a silent fallback under-reports the one line you were reading for. Check which mode produced the diff before you approve it.

**The one-way door: the highest in this skill.** Proprietary table storage, plus years of accumulated history, plus consumers coupled to the schema — three near-irreversible rungs at once, and the exit cost grows every day while the benefit of leaving stays a rate. This is where the export-path question gets asked *before* adoption: is there a documented bulk export, what does the exit cost in shape, and does the data leave in an open format? Storing the corpus in an open table format on object storage keeps the *format* rung two-way even when the *service* rung is one-way, and it is the single highest-leverage move available here.

## 4. NoSQL serving store

**What `modeling-data-engineering` decides.** Access patterns before schema, single-table design, composite keys, secondary indexes, and the deliberate denormalization that comes with them — [`modeling-for-access-patterns.md`](../../modeling-data-engineering/references/modeling-for-access-patterns.md), grounded in AWS's own guidance that you "shouldn't start designing your schema for DynamoDB until you know the questions it will need to answer." That model is a modelling decision that happens to be expressed in a product. It is not decided here and not second-guessed here.

**What is decided here.** Hosting, capacity mode, and replication topology.

`Scaling granularity` is the capacity mode, and the same discipline applies as in archetype 1: state the unit together with the mode that exposes it, from the vendor's own page, for the tier you are actually buying. `Throughput shape` is unusual for this archetype because the generator is application traffic rather than your schedule — `steady` when the store backs a live product, `spiky` when a batch refresh or a campaign drives it. `Exploratory` is the shape this store handles worst: an analyst scanning a serving store is paying request-priced access for an analytical question, and the fix is a copy in archetype 3, not a bigger serving tier.

`Failure and recovery model` carries more weight here than anywhere else, because this store is in a live request path: what the service still answers while degraded, and what the caller does meanwhile, is a design input rather than a runbook detail. Replication topology is a `failure and recovery model` decision *and* a cost decision at once — a cross-region replica is a transfer charge on a recurring basis, so the resilience choice and the egress choice need deciding in the same meeting.

`Operational burden` is where the container-orchestrator question arrives. Running the store of record on a container orchestrator inherits every problem in the frame file, amplified: the orchestrator's design centre is that a workload is replaceable, which is the cattle assumption built into a control loop, and the resources holding your history are the ones it was not written for. Stateless compute there is a platform choice; the store of record there deserves the review budget a near-irreversible decision earns.

**The one-way door: the data model, not the data.** An export path may well exist, and it is still the wrong thing to be reassured by. What leaves is a table whose keys encode another engine's access patterns — the composite keys, the index overloading, the duplication that exists precisely because the reads were known in advance. Ported to a different store, that shape is neither correct nor even meaningful; the migration is a re-modelling exercise against the new engine's read model, run by whoever owns the model rather than whoever owns the infrastructure. This rung is the schema-of-record rung, and its cost is paid by the application on the other end.

## 5. Serving-API hosting

**What `pipelines-architecture-data-engineering` decides.** Whether to serve via an API at all — and [`serving-pipeline-output.md`](../../pipelines-architecture-data-engineering/references/serving-pipeline-output.md) argues, correctly, that for moving whole datasets between data systems a paginated API is close to the worst mechanism available, with a bulk export, a native share or a stream as the better answers. It also owns the contract, and contract and schema versioning follow the data-contract principles in [`data-contracts-and-schema-compatibility.md`](../../quality-data-engineering/references/data-contracts-and-schema-compatibility.md).

**That file defers hosting and infrastructure for a serving API to this domain. This section is where it lands.** What stays out of scope for the whole suite is unchanged: building or operating the API service itself — framework choice, REST versus GraphQL versus gRPC, endpoint implementation, versioning mechanics, API-level auth — is general backend engineering, and this file does not teach it either.

**What is decided here.** Where it runs and how it scales. Three hosting shapes, described by behaviour rather than by product, because the products differ per provider and the shapes do not:

- **A request-scoped runtime that scales to zero.** No standing charge, a cold start on the first request after idle.
- **An always-on container or managed instance.** A standing charge, no cold start, a knob you can turn.
- **A container orchestrator you already operate.** Fine `scaling granularity` and low `coupling`, at an `operational burden` owned by your platform team — and container orchestration itself is platform engineering, outside this skill.

`Throughput shape` picks among them, and it is the same trade as the warm-capacity feature in [`sizing-and-the-cost-model.md`](sizing-and-the-cost-model.md): `spiky` or low-volume request traffic favours the shape that costs nothing while idle; `steady` traffic favours the standing one. `Exploratory` load against an API is a signal that the consumer wanted a query engine, and belongs in archetype 3.

Two axes change character here relative to the rest of the file. `Operational burden` now includes a latency objective and someone paged against it — a batch pipeline that runs late is noticed the next morning, an API that runs late is noticed immediately. And `ecosystem fit` is mostly the identity and network question: the serving API is the component that is *meant* to be reachable, which is exactly what lets the store behind it stop being reachable. Putting the API on a public path and the store on a private one is the placement decision, and [`identity-network-and-encryption.md`](identity-network-and-encryption.md) has the asymmetry that justifies it.

**The one-way door: low, and it is the only archetype where that is the headline.** The service is stateless; it is as reversible as compute, and replacing its hosting is a re-deploy. Everything expensive is behind it, in archetype 3 or 4. What is not low is the contract — but the contract is not this skill's to set, and consumers coupled to it are the schema-of-record rung under someone else's ownership.

## Common mistakes

| Mistake | Why it hurts | Fix |
|---|---|---|
| Choosing a streaming service to fix an ordering or skew problem | Ordering scope, key choice and `acks` are properties of the log, owned by `streaming-data-engineering`, and they survive the purchase unchanged | Fix the key and the guarantee first; then choose the service on the six axes |
| Pricing a streaming migration as an infrastructure project | With a proprietary API the rewrite is the client code, in repositories other teams own and release on their own schedule | Price `coupling` as a cross-team program, and count topic names as consumer-facing identity |
| Spending the design budget on the cluster | Compute is the most reversible rung — reversing it means re-running a job — while the storage, format and schema decisions being made by default are the least | Decide compute quickly and give the deliberation to archetype 3 |
| Declaring an autoscaled cluster's worker count in the infrastructure code | The live count is set by the autoscaler by design; reconciling it pulls capacity from a running job or proposes a replacement | Declare bounds and the policy object; let the count be an output |
| Putting BI and notebook access on a bytes-scanned meter | `Exploratory` load has no ceiling and its driver is invisible to the person pressing run | Give exploratory access a shape with a ceiling, and reserve the scan meter for predictable volume |
| Trusting a removal policy to be the whole story on a bucket with history | CloudFormation errors rather than deleting an S3 bucket containing files, and the CDK escape is a single `autoDeleteObjects` property that reviews like a convenience flag | Treat that property as a near-irreversible change; pair it with provider-side deletion protection and permissions |
| Approving a diff without knowing which mode produced it | `cdk diff --method template` is documented as "less accurate" and reports cosmetic changes as replacements, while `auto` falls back to it silently when the change set cannot be created | Check the mode before reading the replacement lines, and re-run in `auto` with sufficient permissions for a stateful stack |
| Reading a NoSQL export path as an exit | What exports is a table whose keys encode another engine's access patterns; the port is a re-modelling exercise, not a load | Price the exit as model migration owned by whoever owns the model — the schema-of-record rung |
| Running the store of record on a container orchestrator because the platform is already there | The orchestrator's control loop assumes a workload is replaceable, which is the cattle assumption the frame file exists to refute | Stateless compute there is a platform choice; the store of record is a near-irreversible decision and needs that review |
| Treating serving-API hosting as an unowned gap | `pipelines-architecture-data-engineering` decides whether to serve via API and what the contract is, and defers hosting here — the gap is a handover, not a hole | Decide hosting shape against `throughput shape`, and keep the API public so the store need not be |
