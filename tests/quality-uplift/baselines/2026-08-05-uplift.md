# 2026-08-05 uplift campaign — VOID

**Verdict: this campaign is void per spec §6.2.** The score-vs-length Pearson
correlation for this run is **r = 0.61**, above the 0.5 threshold the design spec sets
for trusting a delta. The uplift table below is `analyze.sh`'s real, unedited output —
it is preserved for the record — but it must **not** be read as a standing measurement
of any skill's uplift. Do not cite the per-skill deltas below as evidence the suite
helps or does not help.

Why this run in particular is at risk: with-arm answers averaged **2375 characters**
against the without-arm's **1771** — a 34% length gap. That gap is exactly the confound
§6.2 exists to catch, and the measured r confirms the judge's scores are entangled with
verbosity in this run, not just instructed to ignore it.

Rerunning is not done here — see "What voids a campaign" in `../README.md`. A re-run
would need either a rubric/judge change that breaks the length correlation, or to be
run and reported the same way regardless of outcome.

## Incident during this campaign: duplicate judge writers

While the judging stage (`judge-pairs.sh`) was running, a second, independent
invocation of the same script against the same `results/full/` directory was started
before the first had exited. Both processes appended to `results/full/judgments.jsonl`
concurrently, producing 125 lines across only 63 distinct `(id, rep, judge_rep)` slots —
62 duplicate rows. Each duplicate was a real judge call, but two calls sharing one
`judge_rep` label breaks the order-schedule semantics the "Judge agreement" section
depends on (judge_rep 1/3 same order, judge_rep 2 inverted, one row each).

The contaminated set was not deduplicated in place — choosing which of two competing
rows to keep per slot is a data-selection decision, and making it silently on the set
that produces the headline number is exactly what this eval exists to prevent. Instead:

- the contaminated file is preserved, untouched, at
  `results/full/judgments.contaminated-2runs.jsonl` (125 lines) — kept as evidence, not
  deleted, and **not** used for anything below
- the judging stage was re-run clean, with no competing writer, producing the 63-line
  `results/full/judgments.jsonl` this report is built from
- the 42 answer samples and their `.meta` files were never touched by any of this — only
  the judging stage was affected

Verified before analysis: 63 lines in `judgments.jsonl`, 63 distinct `(id, rep,
judge_rep)` triplets, zero duplicates, `judge-failures.tsv` empty, and the order
schedule intact (`with, without, with` across judge_rep 1/2/3 for every pair).

See `../README.md` for the contamination guard added as a result of this incident.

## Reading the checks, given the void verdict

- **Discards (2, both `A2.with`):** reps 1 and 3, attempt 1 each, both chained
  `superpowers:systematic-debugging` with `pipelines-architecture-data-engineering`
  never firing. Both recovered on retry (attempt 2), so A2 still landed 3/3 valid
  with-arm samples — but it took retries, consistent with A2 also measuring only 4/5 in
  `tests/triggering/baselines/GREEN-crowd-out.md`. This case is measurable, just closer
  to the routing edge than the others.
- **Judge coherence:** zero incoherent rows — every row that stated a preference scored
  that answer at least as high as the other. This check passing does not offset the
  length-correlation failure; they check different things.
- **Judge failures / malformed input:** zero on both counts. The 63-row judgment set and
  42-row `.meta` set were used in full; nothing was silently dropped in `analyze.sh`
  itself.
- **Calibration gates (from Task 3, re-verified before this campaign ran):**
  discrimination gate held 3/3 (scores 8 vs 0/1/0); length-bias gate held 3/3 (specific
  answer, 848 bytes, beat the padded generic answer at 1494 bytes). Both gates passing
  is necessary but not sufficient — they show the judge *can* resist a deliberately
  padded, deliberately generic opponent. A 34% organic length gap between two answers
  that are each trying to be genuinely useful is a subtler case than either calibration
  probe covers, and this run shows the judge did not fully resist it here.

## What would make a re-run trustworthy

Per spec §6.2 and the README: rework the judging design so score and length decouple
before re-running — e.g. tighter rubric anchoring against filler length, or a
length-normalization step in the prompt — and then run the *same* protocol (3 reps,
fixed order schedule, both calibration gates re-verified from raw files) and report
whatever the correlation and the table say, including if the result is again void, small,
zero, or negative.
