# 2026-08-05 uplift campaign — VOID

**Verdict: this campaign is void per spec §6.2.** The score-vs-length Pearson
correlation for this run is **r = 0.61**, above the 0.5 threshold the design spec sets
for trusting a delta. The uplift table below is `analyze.sh`'s real, unedited output —
it is preserved for the record — but it must **not** be read as a standing measurement
of any skill's uplift. Do not cite the per-skill deltas below as evidence the suite
helps or does not help.

Why this run in particular is at risk: the correlation is **within-arm**, which is the
worse of the two possibilities. Decomposing the pooled r by arm, from the same `.meta`
lengths and `judgments.jsonl` scores the report is built from:

```
pooled  n=42  r=0.610
with    n=21  r=0.594   (mean 2375 bytes, mean score 7.40)
without n=21  r=0.651   (mean 1771 bytes, mean score 5.68)
```

Each arm on its own correlates about as strongly as the pool, and the without-arm — the
*shorter* arm — correlates most. Inside one arm the arm label is constant, so nothing
about with-versus-without can be producing that; the judge is rewarding length per se.

There is also a 34% inter-arm length gap (2375 bytes against 1771), and an earlier
version of this file named that gap as the cause. That was wrong. The gap is real but
close to inert here: removing it would leave two within-arm correlations of 0.59 and
0.65 untouched. The VOID verdict stands, and is in fact more robust than the inter-arm
story implied — but a re-run has to target **judge length-bias** (rubric anchoring,
length normalization, or a different judging design), not the length difference between
the arms. Equalizing answer lengths across arms would produce a run that looks cleaner
and is not.

`analyze.sh` now prints the per-arm r alongside the pooled r for exactly this reason: a
pooled number cannot distinguish "the judge is length-biased" from "the with-arm is
longer and better", which is the only question the check exists to answer.

Rerunning is not done here — see "What voids a campaign" in `../README.md`. A re-run
would need either a rubric/judge change that breaks the length correlation, or to be
run and reported the same way regardless of outcome.

## Amendments added 2026-08-07 (no number below is changed)

Four things were found out about *how* this campaign was produced after it was
committed. None of them changes a number in the table below — the campaign is already
void and is not being re-run — but each changes how much the run could ever have been
worth, so it is disclosed here rather than left in a review thread.

**1. This campaign's judge was not blinded in practice, only in its prompt.** The
`judge-pairs.sh` invocation that produced the 63 judgments below ran with no sandbox cwd,
no `--disallowedTools`, and no `--settings`. It therefore kept `Read`, `Glob`, and
`Grep`, ran with the suite skills it was scoring loadable, and inherited the operator's
cwd — `tests/quality-uplift`, which at judging time held `cases.tsv` (the expected skill
per case), `full-answers.log` (lines like `ok A2.with.rep1 chain=…`), and a `results/`
tree where every filename says `with` or `without`. The rubric and both answers reached
it on stdin, so it never needed any of that; it simply had it.

Whether any judge session actually looked is **unfalsifiable**: no judge session log is
saved anywhere. So this is not a claim that the arm labels were read — it is the
statement that nothing in the setup prevented it and nothing recorded it. `judge-pairs.sh`
now runs each judge call from a fresh `mktemp -d` outside the repo, with
`--disallowedTools "Bash" "Read" "Write" "Edit" "Task" "Glob" "Grep"` and the suite
plugin disabled (README contamination guard 4). Any campaign judged before that change —
this one — has to be read as one whose judge structurally could have seen which arm was
which.

**2. "characters" was the wrong unit name.** Answer length is `wc -c`, i.e. bytes. The
prompts and answers are Spanish and contain accented characters, so bytes exceed
characters by roughly 2.4%. The label was corrected to bytes here and in the scripts; the
measured values (2375, 1771, r = 0.61) are unchanged, because bytes is what was always
measured.

**3. The verbatim block below no longer byte-matches current `analyze.sh` output.** It is
the output of the script as it stood on 2026-08-06. Since then the report gained a
per-case judgment-count column, per-arm correlation lines, a duplicate-slot rejection
count, and an unexpected-score-key count. Re-running `./analyze.sh results/full` today
reproduces every number in the table below and adds those lines.

**4. One judgment row's rubric total is inflated above the documented maximum of 8.** In
`P4 rep3 judge_rep2` the judge returned `"tradeeoff": 2` *in addition to* `"tradeoff":
2`. `analyze.sh` totals a score object with `add`, which sums whatever numeric keys are
present, so that row scored 10 on a 0–8 scale. Its effect is small and confined to P4's
with-arm: totalling strictly over the four rubric dimensions instead gives P4 with 7.2
(delta −0.4 rather than −0.1) and moves the with-arm correlation from 0.594 to 0.586 —
pooled r stays 0.610 and the within-arm conclusion in the section above is unchanged
either way. The arithmetic was deliberately **not** changed, because that would restate a
committed campaign's numbers; instead `analyze.sh` now counts and reports such rows, so
the next campaign cannot absorb one silently.

## Incident during this campaign: duplicate judge writers

While the judging stage (`judge-pairs.sh`) was running, a second, independent
invocation of the same script against the same `results/full/` directory was started
before the first had exited. Both processes appended to `results/full/judgments.jsonl`
concurrently, producing 125 lines across only 63 distinct `(id, rep, judge_rep)` slots —
62 duplicate rows. Each duplicate was a real judge call, but two calls sharing one
`judge_rep` label breaks the order-schedule semantics the "Judge agreement" section
depends on (judge_rep 1/3 same order, judge_rep 2 inverted, one row each).

The contaminated set was not deduplicated in place — choosing which of two competing
rows to keep per slot is a data-selection decision, and making it silently on the set
that produces the headline number is exactly what this eval exists to prevent. Instead:

- the contaminated file is preserved, untouched, at
  `results/full/judgments.contaminated-2runs.jsonl` (125 lines) — kept as evidence, not
  deleted, and **not** used for anything below
- the judging stage was re-run clean, with no competing writer, producing the 63-line
  `results/full/judgments.jsonl` this report is built from
- the 42 answer samples and their `.meta` files were never touched by any of this — only
  the judging stage was affected

Verified before analysis: 63 lines in `judgments.jsonl`, 63 distinct `(id, rep,
judge_rep)` triplets, zero duplicates, `judge-failures.tsv` empty, and the order
schedule intact (`with, without, with` across judge_rep 1/2/3 for every pair).

See `../README.md` for the contamination guard added as a result of this incident. As of
2026-08-07 that guard is no longer an operator instruction: both scripts take
`mkdir "$RUN/.lock"` before writing and refuse to start if it is held, and `analyze.sh`
rejects and counts duplicate `(id, rep, judge_rep)` rows instead of reporting a confident
table over them. Fed the preserved 125-line contaminated file, it now reports
`duplicate (id,rep,judge_rep) rows rejected: 62` and marks the table as not a
measurement; before that change it printed a clean-looking table with deltas shifted by
up to 0.9 and `unparseable judgments.jsonl lines: 0`.

## Reading the checks, given the void verdict

- **Discards (2, both `A2.with`):** reps 1 and 3, attempt 1 each, both chained
  `superpowers:systematic-debugging` with `pipelines-architecture-data-engineering`
  never firing. Both recovered on retry (attempt 2), so A2 still landed 3/3 valid
  with-arm samples — but it took retries, consistent with A2 also measuring only 4/5 in
  `tests/triggering/baselines/GREEN-crowd-out.md`. This case is measurable, just closer
  to the routing edge than the others.
- **Judge coherence:** zero incoherent rows — every row that stated a preference scored
  that answer at least as high as the other. This check passing does not offset the
  length-correlation failure; they check different things.
- **Judge failures / malformed input:** zero on both counts. The 63-row judgment set and
  42-row `.meta` set were used in full; nothing was silently dropped in `analyze.sh`
  itself.
- **Calibration gates (from Task 3, re-verified before this campaign ran):**
  discrimination gate held 3/3 (scores 8 vs 0/1/0); length-bias gate held 3/3 (specific
  answer, 848 bytes, beat the padded generic answer at 1494 bytes). Both gates passing
  is necessary but not sufficient — they show the judge *can* resist a deliberately
  padded, deliberately generic opponent on a single hand-built pair. Neither gate
  measures whether score tracks length *across* a set of answers that are all genuinely
  trying to be useful, which is what the within-arm r = 0.59/0.65 above shows it does.
  Both gates passing and the campaign still being void is not a contradiction; it means
  the gates test a coarser failure than the one that occurred.

## What would make a re-run trustworthy

Per spec §6.2 and the README: rework the judging design so score and length decouple
before re-running — e.g. tighter rubric anchoring against filler length, or a
length-normalization step in the prompt — and then run the *same* protocol (3 reps,
fixed order schedule, both calibration gates re-verified from raw files) and report
whatever the correlation and the table say, including if the result is again void, small,
zero, or negative.

Two constraints on that re-run follow from the amendments above. It must target the
judge's length-bias, not the inter-arm length gap: `analyze.sh`'s per-arm r lines are the
pass/fail signal, and a run whose arms happen to be equal in length but whose within-arm r
is still 0.6 is just as void. And it must be judged under the current, structurally
blinded `judge-pairs.sh`, since this campaign's judge was not.
